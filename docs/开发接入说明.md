E16／B16已接入蜂巢城寨（`hive`），只在第7天刷新。Boss出现后，其他非常驻事件（包括未领取的E01R回礼）退场，击败Boss后也不重新刷新；黑市、沃斯商场、地下诊所等常驻入口保留。旧第7天地图档读入后补Boss池，不强行打断旧档正在进行的战斗或对白。旧E16对白／B16战斗／结果页若仍保存五号街区位置，读入时仅将该上下文地点改为hive；回地图后的正常地点访问不改。

2026-10-25对白补全：E16含九句战前与五句战后文本，事件简介在现有任务简报显示。`characters.dancer_black`绑定`dancer_black_dialogue`，使用原样复制的`assets/characters/dancer_black_dialogue_v1.png`（1024×1536 RGBA，`whiteKey:false`，导入启用mipmap；来源及SHA256见同名manifest）。对白各节点显式配置`portraits:{left:"",right:"dancer_black"}`，旧档即使残留其他人物，也只显示黑舞者；主角台词保留，白舞者不在对白中出场。沿用旧节点ID、现有说话者高亮、跳过、战斗与奖励接口；战斗二阶段的黑白舞者配置不变。

一阶段只有黑舞者，10 HP；击倒后瞬间熄屏，停留1秒后直接亮起三道聚光灯，主灯瞬亮。开灯同帧出现一次短促暖白屏闪、加亮灯芯和脚底外扩光环，额外光强在0.65秒内收稳，随后继续操作。稳定灯束每层透明度0.028、光斑0.040；开灯峰值分别为0.058／0.068、灯束宽度增加22%，并叠加暖白灯芯与外扩椭圆光环。二阶段诺伦居中，黑舞者在右、白舞者在左，均与主角脚底水平对齐，各距中央主角420像素，各10 HP，环境持续压暗。两人均击倒才胜利；每人每回合攻击6是本次临时配置。主菜单「战斗演练 → 双人舞者 · Boss」可随时进入，两阶段血量与正式战斗一致，不改冒险进度。

舞者命中特效由`test_stage.gd.show_strike()`按攻击者及动作分派：`dancer_black + pierce`、`dancer_white + slash`共用`dancer_strike_fx.gd`。当前复用诺伦突刺／斩击原纹理，通过独立`dancer_strike_palette.gdshader`转为黑色突刺与白色斩击，保留原图拖尾／月牙／命中爆点层次及透明度。黑突刺绘制480×132、白斩340×170逻辑像素，均大于诺伦对应420×104、270×135的基准；尺寸还随目标纵深与攻击方表现配置缩放。斩击主月牙与命中爆点采用诺伦相同分层锚点，方向整体镜像，动画围绕命中点增长并在后半消退；格挡时略收缩、减弱，0.36秒后自动释放。普通alpha混合保留黑色主体，亮度后调增强灰白枪线及白色月牙／爆点，未更改原透明度，不改诺伦纹理或红色效果；模型、命中时机和其他攻击分派沿用原实现。

`CombatModel.encounter_phase`在完整出牌或回合末由`advance_encounter_phase(player_turn_ended=false, transition={})`推进，转阶段同时开启下一玩家回合。旧手牌弃置、旧玩家回合状态结算一次，再将回合数加1、清格挡、重置回合标记、恢复能量、推进一次科技冷却并正常抽牌（默认5张）。形态、弹药与跨回合能力保留，开局芯片额外抽牌不重发，新舞者本次不行动。弹反／敌方污染路径传`player_turn_ended=true`，跳过已执行的玩家收尾，成功转阶段后跳过普通下一回合分支，避免重复状态、冷却和抽牌。

出牌结果`phaseTurnEvents`返回强制收尾的状态事件，`discarded`包含旧剩余手牌，`drawn`只含新回合抽牌；玩家收尾状态致死时保留事件但`phaseChanged=false`，不揭幕二阶段。视图顺序为旧阶段命中／状态事件、熄屏、重建与揭幕、一次新回合提示、新手牌发出；动画不再结算规则。伤害不会跨阶段。冻结`profile.encounterId="dancer_duet"`、`profile.phaseTwoEnemies`与快照`encounterPhase`；阶段值经整数校验后兼容JSON数字。正式B16胜利出口要求真实二阶段胜利，仍校验阶段、outcome及完整战斗快照。演练在共同的结果类型／忙碌锁／转场锁／revision／场景检查后优先结束，调试弹窗在一、二阶段均可模拟胜利，恢复原冒险并返回菜单，不生成正式奖励或进度。`valid_battle_start()`允许同冻结配置下单敌开局对应双敌当前快照；中途保存仍投影回原开局，继续从一阶段开始。

`Game.flags.dancerBossAppeared`记录Boss出现；`eligible_events()`、入口和刷新池统一过滤非常驻事件，未来显式`permanent:true`事件可保留。当前常驻商店／诊所不是事件池条目。Boss战后先显示原Boss概率卡牌奖励与50信用点，`claim_rewards()`退出E16奖励时设置`flags.week1Complete=true`并保存，随后同一`result`路由优先显示`week_end.gd`，仅含“第一周结束／后续内容开发中”和返回主菜单按钮；普通奖励出口保持回地图。`is_run_failed()`只判断战败，`is_run_over()`同时包含第一周完成，用于封住继续、地图和事件入口；保存／menu／resume不能把完成写成defeat。旧E16 pending奖励继续领取，缺少`creditsStatus`的历史已领取／放弃结果档及完成后地图档迁入周结算；新格式奖励无论先领取哪项，都须显式退出才结束第一周，不重发收益；旧E12完成标记仍清除。后续周不自动开启，演练仍恢复原冒险。

## 被动科技接口（2026-10-24）

定义新增可选`type`，缺省为`active`，被动为`passive`；被动效果仅接受`victory_credits`、`victory_heal`、`opening_draw`与正整数`amount`，不允许`cooldownTurns`／`nextAttackBonus`。`CombatModel.is_passive_cyberware()`统一判别；被动不进入`usedCyberware`或冷却字典，模型和界面均拒绝手动激活。

`CombatModel.draw_cards()`依据冻结profile前四槽，在`turn == 1 && !openingDrawDone`时增加开局抽牌量；首次调用即标记完成，后续抽牌或第二回合不叠加。`battleStart`仍在首次抽牌前捕获，退出重开保持相同七张开局语义，旧快照不自动获得新科技。

`Game.battle_exit("win", revision)`按冻结战斗前四槽记录待领胜利信用点并执行封顶治疗，演练／战败不结算。收益、独立`eventId:battleId:passive_victory`领取凭据、胜利记录和战后节点使用同一草稿保存；失败回滚状态、页面及版本，不提前发送changed。`state.battlePassiveReward`保存收益及可选`creditsStatus`（pending／claimed／skipped，旧记录缺省claimed）；信用点在奖励页汇总到`bonusCredits`后点击领取，治疗在胜利时自动执行。`battle_passive_summary()`供奖励页只读展示；新事件／新战斗清空，旧档缺字段补空，不追发。schema仍为2。演练复制冒险已有与携带列表，结束恢复完整备份，购买的被动科技不因角色默认列表不同被丢弃。

专项`tests/passive_technology_tests.tscn`与扩展的`tests/technology_icons_tests.tscn`；本轮证据分别位于`artifacts/qa/passive-technology-2026-10-24/`和`artifacts/qa/passive-technologies-2026-10-24/`。图标来源与最终提示词见[三枚芯片](../assets/technology/PASSIVE-CHIPS.md)。

## 沃斯商场接口（2026-10-23）

`data/technology_shop.json`保存0—6个`{id,price}`，当前为三项原有主动科技及三枚新增被动芯片、各150，定义在`data/prototype/cyberware.json`，沿用已有科技执行器。`Game.technology_shop_offers()`校验0—6数量、唯一ID、非test_占位、有效定义及正整数价格，返回深拷贝；`buy_shop_technology(index,revision)`检查mall/place、演练／战败／锁、版本、余额和已有状态，通过草稿提交并在保存失败时回滚。购买只扣信用点并加入`ownedCyberwareIds`，不自动携带、不耗时；无新库存字段、补货或schema变更。旧档按现有拥有列表迁移即可购买。

`technology_shop.gd`固定绘制两行三列六货位，当前六项正式科技均配专属PNG／价格／确认框；配置不足六项时仍保留空位且无购买入口，模态期间隔离按钮焦点与Tab／Esc／F1；`main.gd`为mall加载新场景，地图详情提供“进入商场”。背景`woss_mall_shop`的来源、提示词见[素材记录](../assets/market/WOSS-MALL.md)。

本轮发现并修正`valid_noren_state()`原先把能量上限固定为`energyPerTurn`，导致后备能源超基础能量时快照无效。现在从冻结科技定义与本回合激活记录计算上限，继续拒绝非法数值和无来源的超额能量，不改变能量效果或下回合重置规则。

## 分层与事务

`CombatModel` 为纯 RefCounted 模型，不依赖界面节点。负责卡牌实例、抽牌／手牌／弃牌／消耗四个牌区、敌人数组、意图、回合与胜负。`snapshot / restore` 完整序列化局内状态。`battle.gd` 负责目标选择、卡牌飞行动画、意图和血条显示；`Game` 负责自动存档与剧情返回；`main.gd` 负责覆盖全屏的转场和换场。

出牌前校验卡牌仍在手里、目标存活、效果受支持，再统一结算。使用独立实例 UID，所以同一张定义的三张牌也能区分。重复提交、出牌处理、回合切换和转场期间的输入会被拒绝；当前诺伦流程在攻击、退场牌和补牌处理完成后释放忙碌锁。卡牌移动和 HP 在同一逻辑提交内保存，动画只是显示。`battle.gd.start_hand()` 当前依据模型的 `opening_draw_done` 判断首次发牌，新快照保存 `openingDrawDone`；已完成开场抽牌后手牌为空也不重发。仅缺少该字段的旧快照在 `CombatModel.restore()` 中沿用第 1 回合、手牌与弃牌均为空的推断。诺伦消耗区参与四区实例守恒检查；历史恢复专项结果见维护文档，本次未重跑。

新战斗的 `profile` 保存 `playerCharacterId`、`playerAttributes`、`playerSkills`、`playerCyberwareIds`、选定的 `cyberware` 定义和最终牌组。`data/prototype/combat.json` 保留通用敌人、卡牌、补牌和动画规则，里面的 `deck` 仅供底层原型／测试直接构建模型；游戏实际入口会以角色 `startingDeck` 覆盖。正式技能与新属性效果必须先在 CombatModel 中实现并补快照校验和测试，不能把技能元数据当成已生效能力。角色科技列表已控制可激活内容，效果仍由原科技机制执行，见下节。

旧档仍为 schema 2，缺少主角字段时固定迁移到诺伦（即使未来修改新游戏默认角色），旧诺伦头像引用转换为 `@player`；已有 HP、额外牌、冷却、加成与战斗快照不重建。显式保存的未知／NPC 主角 ID 或战斗与冒险的主角 ID 不一致时拒绝读档，并按原流程尝试备用档。

### 新增可玩角色的步骤

1. 在人物表中添加角色 ID、姓名、对话／战斗立绘引用。将图片副本放入工程，在资源表注册路径；根据新立绘校准地图头像裁切。
2. 在可玩角色表中用相同 ID 添加 `attributes.maxHp`、`startingDeck`、`skills` 和 `cyberwareIds`。基础牌 ID 必须在现有卡目录中定义，可重复；尚未设计专属技能时使用 `[]`，不分配科技时也使用 `[]`。目前真正生效的角色属性只有最大 HP，不能仅添加其他属性字段就认为对应规则已经支持。
3. 用 `Game.new_game("角色ID")` 创建该角色的新冒险。不传 ID 时读取默认配置，例如 `Game.new_game()` 目前创建诺伦。此入口创建新冒险，不用于中途切换主角。
4. 在 [data/weeks/week1/events.json](../data/weeks/week1/events.json) 或后续事件配置中接入适合该角色的剧情：当前主角说话使用 `speakerId: "@player"`，正文姓名使用 `{主角姓名}`，其他 NPC 使用各自角色 ID。动态替换姓名不会自动改写角色身份、经历或对白内容。
5. 检查顶部姓名、左右对白立绘、地图头像、战斗立绘和血条，验证基础牌与奖励牌组合、科技列表／顺序／冷却、演练返回、保存／读档。角色立绘尺寸、脚底阴影遮罩、剧情对白适配仍需逐角色验收。

新增普通 NPC 时只需人物表、图片资源与剧情引用；若作为敌人参战，再接入 [data/enemies/enemies.json](../data/enemies/enemies.json) 和对应战斗的 `enemyIds`。NPC 不加入可玩角色表，也不修改新游戏默认主角。

当前正式配置仅有诺伦，属性为 70 HP、基础牌组为十张初始牌（四种 C 牌）、技能列表与初始科技列表均为空。选角界面、冒险中途切换与专属技能效果尚未实现。主菜单的诺伦酒馆背景是已审核的整幅场景插画，未改造成随选角切换的背景。

| 字段 | 用途 |
| --- | --- |
| `poses` | 每个动作的 `texture`（有效 `res://` Texture2D）、`anchor`（两个有限数值）、`scale`（有限正数）；必须有 `idle` |
| `targetRect` | 四个有限数值组成的脚底相对区域 `[x,y,width,height]`，宽高必须为正，继续应用原纵深与镜头变换 |

| `hitEffectTexture` | 咬击特效图片；`bite` 配置必须提供，并包含 `bite`／`bite_close` 两种姿势 |
| `placeholder` | 标记当前形象是否为临时替身，仅作内容说明 |
| `sourceFacing` | 可选`left`（默认）或`right`，镜像纹理与脚底锚点时使用原图朝向 |

## 事件刷新与日期（2026-10-23）

`data/weeks/week1/events.json` 的事件不再含 `optional`。每条事件新增：

```json
"refreshTimeRange": {"startDay": null, "endDay": null}
```

当前8条均为随时。非空端点必须为正整数，起止日为包含边界的日期区间，`null` 表示该侧无限制；与剧情前置同时成立才成为候选。

- `Game.event_refresh_time_label(event)`：展示“随时”或区间。
- `Game.event_in_refresh_range(event, subject={})`：按传入状态日期判断区间；省略状态时使用冒险状态。
- `Game.eligible_events(subject={})`：返回前置／时间符合且未完成的全部候选，按ID排序，不改状态。
- `Game.refresh_event_pool(subject={})`：更新 `refreshedEventIds`，先为合格且未完成的E01R预留一个名额，再保留其余仍合格已有ID，从剩余候选随机补齐至全局最多3个。满池旧档最多让出一个普通事件名额，该事件仍保留为候选；稳定池重复刷新不消耗随机数。新冒险即创建池，每次 `checkpoint()` 统一补池。
- `Game.available_events(place_id="")`：只读返回池内且仍合格事件；按地点查询只过滤同一池，按ID排序，不重新抽取。`start_event()` 再次校验池成员、前置、区间、未完成和地点存在。

冒险仍为schema 2，池随存档持久化；旧schema 2缺字段补池，不回溯修改日期。首次 `completeEvent` 原子地追加ID；E01开幕与E01R回礼不修改日期，其余事件使 `currentDay = min(currentDay + 1, 7)`；重复或失败事务不耗时。`finish` 仍为完成入口，当前六项正式战斗委托均耗时（E03已退役），奖励页不再耗时。日期为1—7的整数，不自动切换 `currentWeek`。地图与共用顶栏保留真实日期和七格进度条。演练恢复完整冒险日期及池。

专项入口：[event_refresh_tests](../tests/story/event_refresh_tests.tscn)，地图模型及完整剧情回归见[测试索引](../tests/README.md)。检查结果以本轮日志和修改记录为准，本文不沿用历史通过数。

目标与状态查询在 `Game`：`map_target_events()` 返回全部已刷新且仍符合条件的事件，`map_place_state(id)` 返回地点、`open`、`available`、`current`、`target`、`completed`、`services`，不再包含 `main_events`／`optional_events`。所有有效地点的 `open` 恒为 `true`。目标及事件按ID稳定排序，落幕后剩余事件继续作为目标。不要把 `state.targetId`（委托对象）或 `activeEventId`（可能停留在上一次事件）当作地图目的地。

普通事件地点复用`place`页面与存档格式，`place.gd`用`task_info_<ID>` Label逐字显示完整标题和描述（80字／秒，先排版再显示，不展示刷新时间），完成后启用`event_<ID>`的“开始任务”按钮。`_start_task()`核对页面、地点、revision和打字完成状态，提交后禁用按钮；实际事件资格仍由`Game.start_event()`校验。多任务用VBox与ScrollContainer排版。动画不写存档；返回／再次进入／继续冒险时重新显示。常驻地点绕过任务简报，诊所进入后才提供治疗；黑市／商场继续由main选择专属视图及原首次对白。旧普通地点存档无事件时仍能返回地图。纹理、坐标与状态标记逻辑不变。

悬停预览与详情卡的文字由 `MidnightMapCard` 自己的 `_label` 创建，只复用 `DemoUI` 的字体与主题；节点加入场景树后再设定受限 `size` 并开启 `clip_text`。文字测量与显示统一使用 Font 的 `BREAK_MANDATORY|BREAK_WORD_BOUND|BREAK_ADAPTIVE`，所有 CardLabel 设 `line_spacing=0`；Font 默认断行 flags 与 `Label.WORD_SMART` 不一致，再加上默认行距，会让 48 像素两行文字只露出一行。预览不使用单行 ellipsis，改动文案或字号后重新检查文字边界。
