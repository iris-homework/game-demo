## 战斗类型（2026-10-23）

`data/battles.json` 的每场战斗可配置 `battleType`：`normal`（普通战斗）、`elite`（精英战斗）、`boss`（Boss战）。现有四场全部显式设为 `normal`，后续分类只需修改对应条目；缺失或非法配置值安全回退为普通。类型不从敌人ID、人数或名称推断；用于卡牌奖励的品级权重，不改变敌人数值或每场1000信用点。

`Game.configured_battle_type(id)` 查询当前配置；`Game.battle_type(id = "")` 优先查询同ID的当前冻结战斗，否则查配置；`Game.battle_type_label(kind)` 提供统一显示文案。`initialize_combat()` 将类型写入 `profile.battleType`，由模型现有深拷贝快照／恢复链路保留，开局快照同步冻结。奖励生成时复制到 `battleReward.battleType`；奖励页读取奖励记录，避免配置更新后改标旧奖励。

存档schema仍为2。旧战斗及奖励缺字段时按普通处理，不按新配置追溯重分类；显式存在的快照／奖励字段必须为三个枚举字符串之一。`valid_combat()`、`valid_battle_reward()` 检查类型，`valid_battle_start()` 继续校验完整profile一致性。演练使用同一初始化入口及原有隔离流程。专项为 `tests/combat/rules/battle_type_tests.tscn`，覆盖三类、冻结、保存恢复、旧档、非法值、奖励不重复领取、演练恢复及无窗口UI结构；不代表目视或物理输入验收。

## 分层与事务

`CombatModel` 为纯 RefCounted 模型，不依赖界面节点。负责卡牌实例、抽牌／手牌／弃牌／消耗四个牌区、敌人数组、意图、回合与胜负。`snapshot / restore` 完整序列化局内状态。`battle.gd` 负责目标选择、卡牌飞行动画、意图和血条显示；`Game` 负责自动存档与剧情返回；`main.gd` 负责覆盖全屏的转场和换场。

出牌前校验卡牌仍在手里、目标存活、效果受支持，再统一结算。使用独立实例 UID，所以同一张定义的三张牌也能区分。重复提交、出牌处理、回合切换和转场期间的输入会被拒绝；当前诺伦流程在攻击、退场牌和补牌处理完成后释放忙碌锁。卡牌移动和 HP 在同一逻辑提交内保存，动画只是显示。`battle.gd.start_hand()` 当前依据模型的 `opening_draw_done` 判断首次发牌，新快照保存 `openingDrawDone`；已完成开场抽牌后手牌为空也不重发。仅缺少该字段的旧快照在 `CombatModel.restore()` 中沿用第 1 回合、手牌与弃牌均为空的推断。诺伦消耗区参与四区实例守恒检查；历史恢复专项结果见维护文档，本次未重跑。

## 可玩主角配置

2026-10-10／0.3.22-characters 已接入 `state.playerCharacterId`。新冒险默认角色由 `data/config.json` 的 `defaultPlayerCharacterId` 指定，目前为 `noren`。`data/player_characters.json` 是可玩角色目录，只放诺伦；`data/characters.json` 仍包含剧情 NPC。两者用同一个角色 ID 关联，不能仅添加 NPC 条目就视为可玩角色。

### 四个配置入口

| 文件 | 接入内容 | 新增角色时如何使用 |
| --- | --- | --- |
| [data/characters.json](../data/characters.json) | 姓名、对话立绘 ID、战斗立绘 ID、地图头像裁切 | 为每个人物添加稳定 ID；可玩角色和 NPC 都从这里读取人物信息 |
| [data/assets.json](../data/assets.json) | 图片资源 ID 与实际文件路径 | 将素材副本放入 `assets/characters/`，登记两种立绘的资源 ID，并让人物表引用这些 ID |
| [data/player_characters.json](../data/player_characters.json) | 属性、初始牌组、专属技能配置与 `cyberwareIds` | 只登记可玩角色；键名与人物表的角色 ID 一致，目前只有 `noren` |
| [data/config.json](../data/config.json) | `defaultPlayerCharacterId` | 指定不传角色 ID 时的新冒险默认主角；添加角色不必修改它，只有更换默认主角时才修改 |

角色 ID 和图片资源 ID 是两个用途：例如诺伦角色 ID 为 `noren`，对话图片资源 ID 为 `noren`，战斗图片资源 ID 为 `noren_battle`。不同角色可以引用不同图片，也可以复用同一资源；配置中的图片 ID 必须对应资源表。

| 字段 | 所在配置 | 当前行为 |
| --- | --- | --- |
| `displayName`、`portraitAssetId`、`battlePortraitAssetId` | `characters.json` | 共用 HUD、对白姓名与立绘、战斗人物、地图头像通过当前主角 ID 读取 |
| `mapAvatarCrop` | `characters.json` | 可选 `[x,y,width,height]`，按原图 0—1 比例裁切头像；诺伦沿用原裁切，其他角色缺字段时显示整图 |
| `attributes.maxHp` | `player_characters.json` | 新冒险与演练的初始／最大 HP；目前诺伦 100。已有存档按保存的 HP 恢复，修改配置不会重置血量 |
| `startingDeck` | `player_characters.json` | 卡 ID 数组，保留重复；新战斗复制后追加 `state.deck` 中的奖励牌，演练只用当前主角基础牌组 |
| `skills` | `player_characters.json` | 专属技能配置数组，目前 `[]`；以后条目元数据需有唯一 `id`、`name`、`description`。可读取并保存到战斗快照，但尚无激活 UI、触发时机或效果执行协议 |
| `cyberwareIds` | `player_characters.json` | 0—4 个不重复科技 ID，按列表顺序显示；引用共用战斗科技目录，空数组或缺字段表示没有科技 |

`Game.player_character_id()`、`player_definition()`、`player_character()`、`player_asset_id(field)` 是当前主角查询入口。`Game.new_game(id)` 可以建立指定角色的新冒险；当前没有在冒险中途切换主角的入口。现有菜单不增加选角界面，仍仅开始诺伦的委托。非法 ID、缺失属性、未知基础牌、损坏的技能元数据及非法科技列表会在开始新冒险前拒绝，保留已有进度。

第一周对白的主角 `speakerId` 使用 `@player`，由 `resolve_character_id()` 解析；NPC 仍使用具体 ID。叙述中使用 `{主角姓名}`，已有 `{目标姓名}` 保持独立。当前存档的 `portraits` 可保存 `@player`。以后明确指向某一固定人物的对白仍可写具体角色 ID。[data/battles.json](../data/battles.json) 的 `participants` 也将主角标为 `@player`，这是参战人物元数据；当前主角显示与战斗初始化直接读取 `state.playerCharacterId`，不靠修改 `participants` 切换主角。

### 游戏中的读取位置

| 游戏位置 | 实现入口 | 读取内容 |
| --- | --- | --- |
| 共用顶部姓名与血条 | [scripts/ui.gd](../scripts/ui.gd) 的 `chrome()`、`refresh_hp()` | 姓名通过 `display_name("@player")` 解析；血量读取当前冒险状态 |
| 剧情对白姓名与立绘 | [scripts/dialogue.gd](../scripts/dialogue.gd)、`DemoUI.portrait()` | 对白 `speakerId` 决定姓名，`state.portraits` 决定左右立绘；主角引用解析为当前角色 ID |
| 地图顶部姓名与当前位置头像 | [scripts/map.gd](../scripts/map.gd)、[map_marker.gd](../scripts/map/map_marker.gd)、[map_assets.gd](../scripts/map/map_assets.gd) | 当前主角姓名、`portraitAssetId` 和 `mapAvatarCrop`；头像缓存按图片与裁切区分 |
| 战斗主角姓名与立绘 | [scripts/battle.gd](../scripts/battle.gd) | 当前主角姓名和 `battlePortraitAssetId`，敌方仍读取敌人配置 |
| 新冒险、初始牌组与演练 | [scripts/game.gd](../scripts/game.gd) 的 `new_game()`、`initialize_combat()`、`start_training()` | 选定角色 ID，读取最大 HP、基础牌组、技能元数据与角色科技列表；演练保留并恢复原冒险 |
| 保存、读档与旧档迁移 | `Game.save_game()`、`load_game()`、`migrate_save()`、`valid_save()` | 保存当前角色，旧档补诺伦 ID；保留已存 HP、奖励牌与战斗进度 |

新战斗的 `profile` 保存 `playerCharacterId`、`playerAttributes`、`playerSkills`、`playerCyberwareIds`、选定的 `cyberware` 定义和最终牌组。`data/prototype/combat.json` 保留通用敌人、卡牌、补牌和动画规则，里面的 `deck` 仅供底层原型／测试直接构建模型；游戏实际入口会以角色 `startingDeck` 覆盖。正式技能与新属性效果必须先在 CombatModel 中实现并补快照校验和测试，不能把技能元数据当成已生效能力。角色科技列表已控制可激活内容，效果仍由原科技机制执行，见下节。

旧档仍为 schema 2，缺少主角字段时固定迁移到诺伦（即使未来修改新游戏默认角色），旧诺伦头像引用转换为 `@player`；已有 HP、额外牌、冷却、加成与战斗快照不重建。显式保存的未知／NPC 主角 ID 或战斗与冒险的主角 ID 不一致时拒绝读档，并按原流程尝试备用档。

### 新增可玩角色的步骤

1. 在人物表中添加角色 ID、姓名、对话／战斗立绘引用。将图片副本放入工程，在资源表注册路径；根据新立绘校准地图头像裁切。
2. 在可玩角色表中用相同 ID 添加 `attributes.maxHp`、`startingDeck`、`skills` 和 `cyberwareIds`。基础牌 ID 必须在现有卡目录中定义，可重复；尚未设计专属技能时使用 `[]`，不分配科技时也使用 `[]`。目前真正生效的角色属性只有最大 HP，不能仅添加其他属性字段就认为对应规则已经支持。
3. 用 `Game.new_game("角色ID")` 创建该角色的新冒险。不传 ID 时读取默认配置，例如 `Game.new_game()` 目前创建诺伦。此入口创建新冒险，不用于中途切换主角。
4. 在 [data/weeks/week1/events.json](../data/weeks/week1/events.json) 或后续事件配置中接入适合该角色的剧情：当前主角说话使用 `speakerId: "@player"`，正文姓名使用 `{主角姓名}`，其他 NPC 使用各自角色 ID。动态替换姓名不会自动改写角色身份、经历或对白内容。
5. 检查顶部姓名、左右对白立绘、地图头像、战斗立绘和血条，验证基础牌与奖励牌组合、科技列表／顺序／冷却、演练返回、保存／读档。角色立绘尺寸、脚底阴影遮罩、剧情对白适配仍需逐角色验收。

新增普通 NPC 时只需人物表、图片资源与剧情引用；若作为敌人参战，再接入 [data/enemies/enemies.json](../data/enemies/enemies.json) 和对应战斗的 `enemyIds`。NPC 不加入可玩角色表，也不修改新游戏默认主角。

当前正式配置仅有诺伦，属性为 100 HP、基础牌组为十张初始牌（四种 C 牌）、技能列表为空、科技列表为异次元口袋、加速时钟、后备能源。选角界面、冒险中途切换与专属技能效果尚未实现。主菜单的诺伦酒馆背景是已审核的整幅场景插画，未改造成随选角切换的背景。

验证入口：`tests/characters/player_character_tests.tscn`、`tests/characters/player_character_visual.tscn`。测试中的第二个角色只存在于内存，不加入正式配置或用户存档。

## 角色科技配置

2026-10-23 更新。当前诺伦的 [player_characters.json](../data/player_characters.json) 配置为：

```json
"cyberwareIds": ["dimensional_pocket", "accelerated_clock", "backup_energy"]
```

共用定义仍在 [data/prototype/cyberware.json](../data/prototype/cyberware.json)，旧六项占位定义保留供历史规则与测试使用。角色的 `cyberwareIds` 是新冒险的起始已有科技及默认携带列表；冒险用 `ownedCyberwareIds` 保留已有科技，用 `equippedCyberwareIds` 保存携带顺序。`Game.player_cyberware(id)` 显式传角色时返回默认列表的深拷贝；不传参数时读取本次冒险的 `equippedCyberwareIds`。`initialize_combat()` 将携带顺序和完整定义冻结在新战斗与演练 profile 中。

| ID | 科技 | effect | 参数 | cooldownTurns |
| --- | --- | --- | --- | --- |
| `dimensional_pocket` | 异次元口袋 | `toggle_stance` | 复用 `change_stance("toggle")` | 3 |
| `accelerated_clock` | 加速时钟 | `redraw_hand` | 先记录手牌张数，再全部弃置并抽等量牌 | 999 |
| `backup_energy` | 后备能源 | `gain_energy` | `amount: 1` | 3 |

冷却计入使用当回合，每次成功进入下一玩家回合减1。例如第1回合使用冷却3的科技，第2／3回合剩余2／1，第4回合可再次使用。切换形态沿用诺伦既有规则：实际切入近战抽2张；切入远程获得下一张攻击减费。换牌可按既有规则回收弃牌堆，也可能抽回刚弃置的牌；空手使用仍进入冷却。额外能量可超过每回合恢复值，下一玩家回合仍重置为配置值。科技没有额外能量消耗。

`CombatModel.valid_cyberware_definition()` 共用于角色配置、激活和快照验证。缺 `effect` 的旧定义按 `next_attack_bonus` 处理，正整数 `nextAttackBonus` 仍有效；缺 `cooldownTurns` 默认1。新定义的效果类型、冷却和能量数值须合法。`toggle_stance`／`gain_energy` 只在诺伦规则下可激活，不能给旧原型战斗套用新资源规则。

角色列表可配置0—4项，界面固定四槽单行居中，已有科技按配置顺序靠左显示，其余槽位显示不可激活的“空位”；空数组或缺字段表示无科技，显示四个空位。空位不计入科技数量，也不绑定数字快捷键。拒绝非数组、非字符串、重复／未知ID、超过四项、目录中重复ID或无效定义。新战斗 profile 保存 `playerCharacterId`、`playerCyberwareIds` 与选定的 `cyberware` 定义，ID列表必须与定义顺序一致。地图已支持本次冒险的科技携带配置；局外科技获取、专属技能和选角界面仍未实现。

地图“科技配置”入口位于“牌库”左侧，打开 `scripts/technology_loadout.gd` 弹层并暂停底层地图。已有列表来自本次冒险的 `ownedCyberwareIds`，新档和旧档迁移取角色 `cyberwareIds` 作为起始值，不额外发放共用目录中保留的历史测试科技。点击已有科技或携带槽即携带／卸下，按选择顺序排列，最多四项，也可全部卸下；每次更改立即调用 `Game.set_technology_loadout(ids, expected_revision)` 随本次冒险保存，只允许正常地图、非演练、无输入锁且版本一致。成功后同步界面版本并保持面板打开，关闭或 Esc 仅返回地图、保留已保存修改；无手动保存或取消按钮。提交失败恢复当前已保存的选择、槽位及高亮，同步版本以便重试并显示失败提示；写盘失败不改变原配置或版本。

冒险 schema 仍为2，新增 `ownedCyberwareIds` 和 `equippedCyberwareIds` 数组，新档默认角色列表，旧档缺字段分别补默认；拥有项须为有效目录ID且无重复，携带项必须是本次冒险已有ID的无重复子集，最多四项，显式空数组不补默认。拥有与携带快照不会因后来修改角色默认列表而被替换。新战斗读取该列表，演练复制有效携带配置并保留冒险备份。已有战斗快照与 `battleStart` 不随配置页改变；Meta不保存本次携带选择，也未新增获取系统。

## 战后奖励接口

`prepare_battle_reward()` 在胜利战后对白的 finish 后生成奖励并发 1000 CR，唯一键防止重复。按开战时冻结的 `battleType` 读取 `data/card_reward_rates.json` 的对应字典；顶层为 `normal`／`elite`／`boss`，每项只含 `B`／`A`／`S` 三个非负整数百分比，合计100。当前分别为60／37／3、50／40／10、0／0／100；C 不参与，没有隐藏保底。现有四场仍全部 `normal`。

`scripts/card_reward_sampler.gd` 是独立的纯抽样逻辑，`valid_rates(rates)` 检查概率表，`sample(catalog, rates, count = 3)` 先按品级权重抽取，再在该级剩余卡 ID 中等概率选卡，返回不重复的候选数组。同级候选耗尽后只在仍有卡的正权重品级间归一化；配置非法或正权重候选不足时返回空数组。`Game` 先成功生成三张再到账和添加领取键，失败提示配置错误。

新正式战斗和演练均使用当前主角基础牌组加 `state.deck`。演练开始复制拥有牌，退出恢复完整冒险；不写盘、不发奖，演练中拒绝永久加牌。进行中的战斗保留自己的目录、牌区、状态、能力和 openingDrawDone 标记，不因目录更新重建。存档 schema 仍为 2。

**唯一解析入口**为 `Game.enemy_combat_visual(enemy)`，它转交 `EnemyVisualResolver.resolve()`，集中完成存档／当前目录引用选择、字段校验、图片加载和整体回退，返回已验证的 `Visual`。`battle.gd` 把结果数组传给战场；`pose_actor.setup_enemy()` 只接收结果，不读取 Game 或原始 JSON，不再自建加载／回退分支。

| 字段 | 用途 |
| --- | --- |
| `poses` | 每个动作的 `texture`（有效 `res://` Texture2D）、`anchor`（两个有限数值）、`scale`（有限正数）；必须有 `idle` |
| `targetRect` | 四个有限数值组成的脚底相对区域 `[x,y,width,height]`，宽高必须为正，继续应用原纵深与镜头变换 |
| `poseAliases` | 缺少专用动作时的一步映射，目标必须是已有姿势；鱼为 `{"block":"idle"}` |
| `attackStyleOverride` | 允许空字符串、`slash`、`pierce`、`bite`、`shoot`、`laser`；空字符串沿用动作请求，`bite`／`shoot`／`laser`需有对应姿势；laser还需掌心与掌宽校准 |
| `hitEffectTexture` | 咬击特效图片；`bite` 配置必须提供，并包含 `bite`／`bite_close` 两种姿势 |
| `placeholder` | 标记当前形象是否为临时替身，仅作内容说明 |
| `sourceFacing` | 可选`left`（默认）或`right`，镜像纹理与脚底锚点时使用原图朝向 |
| `poses.*.whiteKey` | 可选bool，仅RGB白底姿势启用既有去白材质；归位残影同步处理 |

敌人实例另可带`formationSlot`，使用上述三个三角槽位；不配置时沿用既有纵深布局。

新战斗会随敌人定义保留可选的 `combatVisualId`。解析顺序为：有效的快照形象 → 当前敌人库形象 → 有效的 `finn` 配置 → 内置 Finn 待机图。每个候选都必须完整校验通过，字段缺失、错误类型、越界／非有限数值、缺图／非图片资源、非法别名或不完整攻击配置会整套拒绝，留下诊断，不把部分结果交给角色。若 JSON 缺失、无法解析或根节点不是对象，也通过同一入口返回内置待机图。内置回退只保留一张图和脚底校准，其余请求回到待机，不复制完整动画目录。

旧快照没有形象字段时查询当前敌人；保存的形象已改名／删除或内容损坏时，也先尝试当前敌人配置。有效的快照引用仍优先。所有解析均不回写快照、目录或存档，不改变存档版本、生命、意图或伤害。目录随流程实例加载，恢复画面时重新验证当前资源，没有跨战斗保存的解析缓存。

主角与敌人分别通过 `setup_player()`／`setup_enemy()` 初始化，角色侧的 `is_player` 标志控制持枪姿态、形态特效及枪口校准。`kind` 只用于标记形象 ID；敌人形象即使命名为 `noren`，也会读取该敌人的配置。诺伦既有图片、形态切换及所有动作节奏保留。新增全新动画机制仍需实现对应演出，并在解析器的支持样式与校验中注册，不能只填写任意样式名。

验证入口：`tests/combat/enemies/enemy_visual_library_tests.tscn` 直接检查正式目录与已发布目录，不经过制作台的临时路径修补；覆盖全部正式敌人的实际姿势纹理、已发布外观、专属特效绑定、新旧快照、损坏配置、分级回退，以及鱼咬击、机器人掌心射线和黑帮突刺的命中回调。`enemy_asset_pipeline/test/enemy_resource_paths.test.cjs` 已纳入 `npm test`，检查两个目录全部资源引用的存在性与路径大小写。`tests/combat/enemies/fish/fish_enemy_visual.tscn` 检查实际战斗，支持 `-- --output-dir <目录>` 保存本轮证据。

## 回合与动画

当前诺伦规则每回合 3 能量、补牌目标 5 张，结束回合弃置剩余手牌，抽牌堆空时回收弃牌并洗牌。卡牌伤害按定义和形态计算；B11正式与演练均为双鱼各30 HP，B04为15／15／30 HP黑帮三人战；B02正式生命值回退为3 HP、演练100 HP，意图为单次攻击10。其余演练默认100 HP，其余正式剧情敌人使用3 HP／攻击1原型回退。旧战斗保留自己的规则快照，不能以旧测试牌攻击 1 推断诺伦新规则。

`battle.gd` 在模型完成出牌后立即提交，再按返回的逐段命中记录播放攻击与状态变化；已使用或弃置的牌立即从交互字典移除，关闭鼠标拦截。攻击、退场牌与补牌处理完成后释放忙碌锁。结束回合先播放弃牌与提示，再统一结算一次模型并提交，后续动画只展示结果。实际参数以当前脚本为准，完整输入和显示边界见[卡牌与效果实现维护指南](卡牌与效果实现维护指南.md)。

进入与退出战斗的花屏由 `shaders/glitch.gdshader` 实现。主场景先锁输入，自下向上覆盖，遮满后替换视图，再淡出。胜利、失败及演练退出共用同一条路径。当前时长为覆盖 0.58 秒、消退 0.32 秒。

## 剧情返回和演练

每场战斗通过 win、lose 返回对应节点；旧 surrender 节点仅用于旧档兼容，结果接口不再接受投降。模型 outcome 只通知视图结束战斗，视图调用 `Game.battle_exit(result, revision)`；由流程管理器保存结果和历史，再进入正确节点。成功完成战后对白才标记事件完成。开发模拟按钮也使用同一接口。

## 事件刷新与日期（2026-10-23）

`data/weeks/week1/events.json` 的事件不再含 `optional`。每条事件新增：

```json
"refreshTimeRange": {"startDay": null, "endDay": null}
```

当前5条均为随时。非空端点必须为正整数，起止日为包含边界的日期区间，`null` 表示该侧无限制；与剧情前置同时成立才成为候选。

- `Game.event_refresh_time_label(event)`：展示“随时”或区间。
- `Game.event_in_refresh_range(event, subject={})`：按传入状态日期判断区间；省略状态时使用冒险状态。
- `Game.eligible_events(subject={})`：返回前置／时间符合且未完成的全部候选，按ID排序，不改状态。
- `Game.refresh_event_pool(subject={})`：更新 `refreshedEventIds`，保留仍合格已有ID，从其余候选随机补齐至全局最多3个。新冒险即创建池，每次 `checkpoint()` 统一补池。
- `Game.available_events(place_id="")`：只读返回池内且仍合格事件；按地点查询只过滤同一池，按ID排序，不重新抽取。`start_event()` 再次校验池成员、前置、区间、未完成和地点存在。

冒险仍为schema 2，池随存档持久化；旧schema 2缺字段补池，不回溯修改日期。首次 `completeEvent` 原子地追加ID并使 `currentDay = min(currentDay + 1, 7)`；重复或失败事务不耗时。`finish` 仍为完成入口，因此E01、付费E03及战斗事件一致，奖励页不再耗时。日期为1—7的整数，不自动切换 `currentWeek`。地图与共用顶栏保留真实日期和七格进度条。演练恢复完整冒险日期及池。

专项入口：[event_refresh_tests](../tests/story/event_refresh_tests.tscn)，地图模型及完整剧情回归见[测试索引](../tests/README.md)。检查结果以本轮日志和修改记录为准，本文不沿用历史通过数。

冒险 `schemaVersion` 当前为2。版本1升级会初始化 `maxHp/currentHp=100`、`currentDay=1`、空 `combat` 和 `inventory`。`migrate_save()` 还对缺少字段的 schema 2 存档补主角、奖励、对话记录、科技配置和刷新池（保留日期，不追算已完成事件耗时），并经 `migrate_mercenary_story()` 处理已删除的阵营剧情引用；不是只有版本数字升级。战斗恢复的可选字段缺省由 `CombatModel.restore()` 处理。`valid_combat()` 校验 UID 不重复、敌方生命范围及牌区实例守恒，诺伦的消耗区也参与检查；新增效果仍需维护对应执行与校验。完整保留和清理边界见[存档维护与恢复](维护文档.md#存档维护与恢复)。

`healHpPercent` 按最大 HP 计算并封顶。医院和地下诊所通过 `Place.services` 调用同一动作。2026-10-23 地下诊所服务配置 `creditsCost: 150`，每次支付150信用点恢复30%最大HP；未配置费用的医院继续免费。`Game.healing_service(place_id)` 提供共用展示与可用性信息，`heal_at()` 在同一事务中扣款并治疗；余额不足或满血时不扣款，不推进日期。`advanceDay` 仅由明确请求或开发工具调用，日期封顶第7天，不自动进入下一周；事件首次 `completeEvent` 同一事务推进1天（第7天封顶），重复完成不再耗时。

MetaProfile 使用独立文件，schemaVersion=1，cyberwareState 初始为空。新游戏不清除 MetaProfile。当前科技页面只作内容入口，不修改战斗属性。

当前战斗科技（2026-10-23）：诺伦配置异次元口袋、加速时钟、后备能源；定义、冷却计时、快照与旧战斗兼容统一见[角色科技配置](#角色科技配置)。局外页面仍不提供获取或装备。

## 地图接口

2026-10-16 删除地点解锁机制：17 个地点全部默认开放，`places.json` 不再配置 `unlockCondition` 或 `lockHint`。进入地点、治疗及事件入口只检查地点存在，不求值地点条件。事件自身的前置条件仍生效。旧存档直接读取新规则，无需迁移。

2026-10-11 已修复消费端固定读取 `city_map` 的问题：配置中的 `cityMapAssetId` 决定实际显示的底图。字段缺省使用 `city_map`，空值或资源不可用沿用原有地图后备纹理。新增底图时同时注册 `data/assets.json` 的资源、设置 `data/map.json` 的 ID，并核对下述原城市区域与地点锚点映射。`tests/map/map_config_tests.tscn` 是资源替换、缺省／失效后备和绘制比例的检查入口，本次未运行。

地图读取 `data/map.json` 的总览插画资源，`cityMapAssetId` 当前为 `city_map_expanded`，经 [data/assets.json](../data/assets.json) 指向 `assets/map/map-expanded-v1.png`；旧 `city_map`／`map.jpg` 保留作来源与后备资源。该资源的 `mapContentRect` 是原城市在扩绘图中的归一化区域。`map.gd._build_map()` 以此区域计算 `map_rect`，再得到完整底图的 `_art_rect`；底图保持原始比例，缩放／拖动边界使用完整底图。`coordinatesStatus` 当前为 `illustration-calibrated`，[data/places.json](../data/places.json) 的17个 `mapAnchor`（0—1比例坐标）映射到原城市的 `map_rect`，并非整张扩绘图。

保持原城市构图的扩绘可校准 `mapContentRect` 并保留已有 `mapAnchor`；城市内部布局改变时须重校对应锚点，未配置 `mapContentRect` 时默认整张图为内容区域。`mapDisplay` 的 `offset`／`labelOffset`／`avatarSide` 只用于展示，`hitArea` 是元数据，实际点击命中取自图钉与头像的当前尺寸。资源替换后分别核对原城市位置、完整图边界和地点标记，不能直接把旧锚点按扩绘全图比例重算。

目标与状态查询在 `Game`：`map_target_events()` 返回全部已刷新且仍符合条件的事件，`map_place_state(id)` 返回地点、`open`、`available`、`current`、`target`、`completed`、`services`，不再包含 `main_events`／`optional_events`。所有有效地点的 `open` 恒为 `true`。目标及事件按ID稳定排序，落幕后剩余事件继续作为目标。不要把 `state.targetId`（委托对象）或 `activeEventId`（可能停留在上一次事件）当作地图目的地。

事件角标只按战斗类型分组：普通黄色感叹号、精英红色感叹号、Boss彩色霓虹故障骷髅头；数量按类型合计。详情及地点页显示“刷新时间：随时”或配置区间，不显示事件类别。点击地点标记打开浮动详情卡，命中范围是标记本身；底部按钮为“进入地点 →”，按钮再次调用 `start_event()`、`visit()` 或 `heal_at()` 校验。地图治疗不修改 `currentPlaceId`，通过 `pending_selection_id` 恢复详情。纹理经 `ResourceLoader` 读取，在运行时像素副本裁切／降采样／生成mipmaps，不改源素材；外框由 `scripts/map/frame_state.gdshader` 染色。

悬停预览与详情卡的文字由 `MidnightMapCard` 自己的 `_label` 创建，只复用 `DemoUI` 的字体与主题；节点加入场景树后再设定受限 `size` 并开启 `clip_text`。文字测量与显示统一使用 Font 的 `BREAK_MANDATORY|BREAK_WORD_BOUND|BREAK_ADAPTIVE`，所有 CardLabel 设 `line_spacing=0`；Font 默认断行 flags 与 `Label.WORD_SMART` 不一致，再加上默认行距，会让 48 像素两行文字只露出一行。预览不使用单行 ellipsis，改动文案或字号后重新检查文字边界。

## 牌堆浏览

`pile_view.gd` 是战斗内的模态大界面，使用 ScrollContainer + 五列 GridContainer，复用 CombatCard 的 read_only 预览模式（1.2 倍卡面、不触发选牌、不阻挡滚轮）。网格从内容区域最左侧开始排列，不足一行也不居中。重复实例逐张展示；Esc、右键与返回按钮关闭。浏览时拦截战斗鼠标与快捷键，关闭后恢复原战斗。

展示顺序只对 contents 的副本排序：排序值取可选整数 sortOrder，未填写则取 card_catalog 中的位置；同优先级按卡牌 ID、同卡按稳定实例 UID 排列。不会写回实际 draw_pile / discard_pile，也不会泄露临时洗牌结果。

`tests/combat/interaction/pile_visual.tscn` 覆盖空牌堆、真实弃牌、30 张临时容量样本、重复卡、默认／显式排序、滚轮穿过卡面、末行完整可见、输入隔离和关闭。容量样本只在测试内存中生成，不加入正式牌组或存档。

手牌使用 BUTTON_PRESS，在鼠标按下时立即选中并更新指向线。battle.gd 记录本次按住的卡牌 UID；左键松开时重新检测有效目标并只结算一次。空白处松开保留点选模式；取消、出牌与回合忙碌会清理按住状态。只读牌堆卡不启用此输入模式。`tests/combat/interaction/drag_visual.tscn` 验证按下起线、拖动松开出牌、取消、重复释放和原点选方式。
