# R1 卡牌战斗开发接入说明

当前工程为 **0.3.23-character-cyberware**；角色及义体接入章节于 **2026-10-11（Asia/Shanghai）** 核对代码与配置。其他章节保留各自的历史验证范围，地图页面于 2026-10-07 接入。修改前先阅读 [维护文档](维护文档.md)，历史变化见 [修改记录](修改记录.md)。本说明中的预留接口不等于正式规则已经实现。

## 分层与事务

`CombatModel` 为纯 RefCounted 模型，不依赖界面节点。负责卡牌实例、三个牌堆、敌人数组、意图、回合与胜负。`snapshot / restore` 完整序列化局内状态。`battle.gd` 负责目标选择、卡牌飞行动画、意图和血条显示；`Game` 负责自动存档与剧情返回；`main.gd` 负责覆盖全屏的转场和换场。

出牌前校验卡牌仍在手里、目标存活、效果受支持，再统一结算。使用独立实例 UID，所以同一张定义的三张牌也能区分。重复提交、出牌起手、回合切换和转场期间的输入会被拒绝；命中后的视觉收尾不阻塞下一次出牌。卡牌移动和 HP 在同一逻辑提交内保存，动画只是显示。当前默认原型已验证战斗快照恢复；0.3.19-rewards 用首回合空手且弃牌为空识别首次发牌，修复扩展牌组首回合打空后的恢复；未来消耗／移除效果仍需单独发牌标记，不能对任意扩展规则作无条件恢复保证。

## 可玩主角配置

2026-10-10／0.3.22-characters 已接入 `state.playerCharacterId`。新冒险默认角色由 `data/config.json` 的 `defaultPlayerCharacterId` 指定，目前为 `noren`。`data/player_characters.json` 是可玩角色目录，只放诺伦；`data/characters.json` 仍包含剧情 NPC。两者用同一个角色 ID 关联，不能仅添加 NPC 条目就视为可玩角色。

### 四个配置入口

| 文件 | 接入内容 | 新增角色时如何使用 |
| --- | --- | --- |
| [data/characters.json](../data/characters.json) | 姓名、对话立绘 ID、战斗立绘 ID、地图头像裁切 | 为每个人物添加稳定 ID；可玩角色和 NPC 都从这里读取人物信息 |
| [data/assets.json](../data/assets.json) | 图片资源 ID 与实际文件路径 | 将素材副本放入 `assets/characters/`，登记两种立绘的资源 ID，并让人物表引用这些 ID |
| [data/player_characters.json](../data/player_characters.json) | 属性、初始牌组、专属技能配置与 `cyberwareIds` | 只登记可玩角色；键名与人物表的角色 ID 一致，目前只有 `noren` |
| [data/config.json](../data/config.json) | `defaultPlayerCharacterId` | 指定不传角色 ID 时的新冒险默认主角；添加角色不必修改它，只有更换默认主角时才修改 |

角色 ID 和图片资源 ID 是两个用途：例如诺伦角色 ID 为 `noren`，对话图片资源 ID 为 `noren`，战斗图片资源 ID 为 `noren_battle`。不同角色可以引用不同图片，也可以复用同一资源；配置中的图片 ID 必须对应资源表。

| 字段 | 所在配置 | 当前行为 |
| --- | --- | --- |
| `displayName`、`portraitAssetId`、`battlePortraitAssetId` | `characters.json` | 共用 HUD、对白姓名与立绘、战斗人物、地图头像通过当前主角 ID 读取 |
| `mapAvatarCrop` | `characters.json` | 可选 `[x,y,width,height]`，按原图 0—1 比例裁切头像；诺伦沿用原裁切，其他角色缺字段时显示整图 |
| `attributes.maxHp` | `player_characters.json` | 新冒险与演练的初始／最大 HP；目前诺伦 100。已有存档按保存的 HP 恢复，修改配置不会重置血量 |
| `startingDeck` | `player_characters.json` | 卡 ID 数组，保留重复；新战斗复制后追加 `state.deck` 中的奖励牌，演练只用当前主角基础牌组 |
| `skills` | `player_characters.json` | 专属技能配置数组，目前 `[]`；以后条目元数据需有唯一 `id`、`name`、`description`。可读取并保存到战斗快照，但尚无激活 UI、触发时机或效果执行协议 |
| `cyberwareIds` | `player_characters.json` | 0—6 个不重复义体 ID，按列表顺序显示；引用共用临时义体目录，空数组或缺字段表示没有义体 |

`Game.player_character_id()`、`player_definition()`、`player_character()`、`player_asset_id(field)` 是当前主角查询入口。`Game.new_game(id)` 可以建立指定角色的新冒险；当前没有在冒险中途切换主角的入口。现有菜单不增加选角界面，仍仅开始诺伦的委托。非法 ID、缺失属性、未知基础牌、损坏的技能元数据及非法义体列表会在开始新冒险前拒绝，保留已有进度。

第一周对白的主角 `speakerId` 使用 `@player`，由 `resolve_character_id()` 解析；NPC 仍使用具体 ID。叙述中使用 `{主角姓名}`，已有 `{目标姓名}` 保持独立。当前存档的 `portraits` 可保存 `@player`。以后明确指向某一固定人物的对白仍可写具体角色 ID。[data/battles.json](../data/battles.json) 的 `participants` 也将主角标为 `@player`，这是参战人物元数据；当前主角显示与战斗初始化直接读取 `state.playerCharacterId`，不靠修改 `participants` 切换主角。

### 游戏中的读取位置

| 游戏位置 | 实现入口 | 读取内容 |
| --- | --- | --- |
| 共用顶部姓名与血条 | [scripts/ui.gd](../scripts/ui.gd) 的 `chrome()`、`refresh_hp()` | 姓名通过 `display_name("@player")` 解析；血量读取当前冒险状态 |
| 剧情对白姓名与立绘 | [scripts/dialogue.gd](../scripts/dialogue.gd)、`DemoUI.portrait()` | 对白 `speakerId` 决定姓名，`state.portraits` 决定左右立绘；主角引用解析为当前角色 ID |
| 地图顶部姓名与当前位置头像 | [scripts/map.gd](../scripts/map.gd)、[map_marker.gd](../scripts/map/map_marker.gd)、[map_assets.gd](../scripts/map/map_assets.gd) | 当前主角姓名、`portraitAssetId` 和 `mapAvatarCrop`；头像缓存按图片与裁切区分 |
| 战斗主角姓名与立绘 | [scripts/battle.gd](../scripts/battle.gd) | 当前主角姓名和 `battlePortraitAssetId`，敌方仍读取敌人配置 |
| 新冒险、初始牌组与演练 | [scripts/game.gd](../scripts/game.gd) 的 `new_game()`、`initialize_combat()`、`start_training()` | 选定角色 ID，读取最大 HP、基础牌组、技能元数据与角色义体列表；演练保留并恢复原冒险 |
| 保存、读档与旧档迁移 | `Game.save_game()`、`load_game()`、`migrate_save()`、`valid_save()` | 保存当前角色，旧档补诺伦 ID；保留已存 HP、奖励牌与战斗进度 |

新战斗的 `profile` 保存 `playerCharacterId`、`playerAttributes`、`playerSkills`、`playerCyberwareIds`、选定的 `cyberware` 定义和最终牌组。`data/prototype/combat.json` 保留通用敌人、卡牌、补牌和动画规则，里面的 `deck` 仅供底层原型／测试直接构建模型；游戏实际入口会以角色 `startingDeck` 覆盖。正式技能与新属性效果必须先在 CombatModel 中实现并补快照校验和测试，不能把技能元数据当成已生效能力。角色义体列表已控制可激活内容，效果仍由原义体机制执行，见下节。

旧档仍为 schema 2，缺少主角字段时固定迁移到诺伦（即使未来修改新游戏默认角色），旧诺伦头像引用转换为 `@player`；已有 HP、额外牌、冷却、加成与战斗快照不重建。显式保存的未知／NPC 主角 ID 或战斗与冒险的主角 ID 不一致时拒绝读档，并按原流程尝试备用档。

### 新增可玩角色的步骤

1. 在人物表中添加角色 ID、姓名、对话／战斗立绘引用。将图片副本放入工程，在资源表注册路径；根据新立绘校准地图头像裁切。
2. 在可玩角色表中用相同 ID 添加 `attributes.maxHp`、`startingDeck`、`skills` 和 `cyberwareIds`。基础牌 ID 必须在现有卡目录中定义，可重复；尚未设计专属技能时使用 `[]`，不分配义体时也使用 `[]`。目前真正生效的角色属性只有最大 HP，不能仅添加其他属性字段就认为对应规则已经支持。
3. 用 `Game.new_game("角色ID")` 创建该角色的新冒险。不传 ID 时读取默认配置，例如 `Game.new_game()` 目前创建诺伦。此入口创建新冒险，不用于中途切换主角。
4. 在 [data/weeks/week1/events.json](../data/weeks/week1/events.json) 或后续事件配置中接入适合该角色的剧情：当前主角说话使用 `speakerId: "@player"`，正文姓名使用 `{主角姓名}`，其他 NPC 使用各自角色 ID。动态替换姓名不会自动改写角色身份、经历或对白内容。
5. 检查顶部姓名、左右对白立绘、地图头像、战斗立绘和血条，验证基础牌与奖励牌组合、义体列表／顺序／冷却、演练返回、保存／读档。角色立绘尺寸、脚底阴影遮罩、剧情对白适配仍需逐角色验收。

新增普通 NPC 时只需人物表、图片资源与剧情引用；若作为敌人参战，再接入 [data/enemies/enemies.json](../data/enemies/enemies.json) 和对应战斗的 `enemyIds`。NPC 不加入可玩角色表，也不修改新游戏默认主角。

当前正式配置仅有诺伦，属性为 100 HP、基础牌组为五张临时攻击、技能列表为空、义体列表为现有临时义体 01—06。选角界面、冒险中途切换与专属技能效果尚未实现。主菜单的诺伦酒馆背景是已审核的整幅场景插画，未改造成随选角切换的背景。

验证入口：`tests/player_character_tests.tscn`、`tests/player_character_visual.tscn`。测试中的第二个角色只存在于内存，不加入正式配置或用户存档。

## 角色义体配置

2026-10-11／0.3.23-character-cyberware 接入。正式可玩目录仍只有诺伦，在 [player_characters.json](../data/player_characters.json) 中配置：

```json
"cyberwareIds": [
  "test_cyberware_01", "test_cyberware_02", "test_cyberware_03",
  "test_cyberware_04", "test_cyberware_05", "test_cyberware_06"
]
```

[data/prototype/cyberware.json](../data/prototype/cyberware.json) 继续作为共用定义目录，保存名称、说明和 `nextAttackBonus`，原六项定义未改动。角色配置只引用 ID，不复制效果。`Game.cyberware_definition(id)` 查询目录；`Game.player_cyberware(id)` 按角色列表取出定义并返回深拷贝，省略参数时读取当前主角。`initialize_combat()` 为新战斗与演练覆盖通用原型的义体目录，列表顺序同时决定卡面与数字键顺序。

列表可配置 0—6 项；空数组或缺字段表示无义体，界面显示“当前角色没有可激活义体”。非数组、非字符串、重复／未知 ID、超过六项、目录中重复 ID，以及被引用定义缺少名称／说明或加成不是正整数时，角色配置无效，开始新冒险前拒绝并保留原进度。加入不同效果前需扩展 CombatModel、存档校验和测试，不能仅添加 JSON 字段。

新战斗 profile 保存 `playerCharacterId`、`playerCyberwareIds` 及选定的完整 `cyberware` 定义；ID 列表必须与快照定义顺序一致。读档按保存的定义、`usedCyberware` 和 `nextAttackBonus` 恢复，后续修改角色列表不重配进行中的战斗，下次新战斗才使用更新配置。旧档已有义体定义不替换、不补新标记；旧八项快照沿用前六项可激活及旧加成保留的兼容规则。仅当旧战斗缺少义体配置时，按该存档的角色补入；缺角色 ID 的旧档先固定归属诺伦。

诺伦仍每张下次有效攻击 +1、多张叠加、每张当回合使用后冷却，下个玩家回合恢复；无效出牌不消耗加成，未使用加成跨回合保留。义体不进入抽牌／手牌／弃牌堆。角色独立配置已经参与战斗；正式局外装备、获取、角色装备存档与专属技能执行尚未加入，`meta_profile.json` 及空的正式义体目录保持现状。

验证入口：`tests/character_cyberware_tests.tscn` 检查角色隔离、配置校验、效果、演练和新旧存档；`tests/character_cyberware_visual.tscn` 用实际界面检查两项／空列表／返回诺伦与数字键顺序；`tests/cyberware_visual.tscn` 保留诺伦六卡的真实攻击与冷却回归。临时角色仅存在于测试内存，正式配置仍只有诺伦。

主菜单总牌库接口于 0.3.20-library 加入：`Game.library_cards()` 合并 `card_catalog`、`prototype_rules.cards`、`reward_rules.cards`，按 ID 去重，正式定义优先，按 `sortOrder` 再 ID 排序，返回深拷贝。`open_card_library()` 仅允许从 menu 进入、遵守忙碌锁，只改页面不改冒险检查点。`scripts/card_library.gd` 用 `CombatCard.setup(..., true)` 展示只读七列网格，0.3.21 起填满游戏画布、仅保留 84px 顶栏，一屏可完整显示 21 张，超出可滚动；右上角 close_button 或 Esc 返回主菜单；不实例化战斗、不读取拥有数量。新增正式卡会自动收录，总牌库不收录独立义体系统的卡片。

## 战后奖励接口（0.3.19-rewards）

`prepare_battle_reward()` 在正式胜利的战后对白到达 `finish` 后调用，自动到账配置的 1000 CR。唯一领取键为 `事件:战斗:victory`，存入 `claimedRewardIds`；`battleReward` 保存 eventId、battleId、claimId、credits、options、selectedCardId、status（pending／claimed／skipped）。`choose_reward_card(id, revision)` 同时追加 `state.deck` 和消费选卡机会，再创建检查点。退出 `claim_rewards()` 时未选卡记为 skipped。

`state.deck` 当前表示获得的额外卡 ID，保留重复卡。`initialize_combat()` 为正式战斗复制通用 profile，用当前主角 `startingDeck` 覆盖基础牌组，再追加这些卡并合入测试奖励定义；演练只用当前主角的基础牌组（诺伦为五张），进行中的快照保留自己的卡目录。schema 2 旧档迁移补空 `battleReward`，旧结果页不追补奖励；在战后对白的旧档到达 finish 时可获得奖励。新增字段在 `valid_battle_reward()` 中校验。

界面沿用 `result` 路由，由 `result.gd` 加载 `reward.gd`；三选一弹层禁止底层鼠标与焦点操作，Esc 先关闭选卡。三张卡目前同为攻击 1，无费用；正式奖励池仍未设计。奖励规则／存档用 `reward_tests.tscn`，真实窗口输入／截图用 `reward_visual.tscn`。

当前只实现 `effects: [{"type":"damage","amount":1}]`。未知效果拒绝提交；能量、格挡、状态、升级、消耗、稀有度与正式牌组构筑均未实现。后续应在模型中扩展效果处理和校验，保持视图只消费结果。cost 为 null 时显示测试无费用，不产生虚构能量值。

临时卡视觉由 `CombatCard` 绘制青色切角框、线路纹样与选中洋红轮廓，正式卡图通过资源 ID 加载。卡牌文字与规则数据分离。当前原型手牌为三张；更多卡牌时应继续校验扇形间距、悬停和文本高度。

## 新增敌人和意图

`data/enemies/enemies.json` 每项包括 id、characterId、displayName、battlePortraitAssetId、maxHp、intentSequence。当前单敌战斗是验收范围；模型保存 enemies 数组，未来扩展多敌时需相应调整战场布局与目标规则。

maxHp=null、intentSequence=[] 时使用临时 profile 的 HP 3 与攻击 1，正式参数不冒充已定稿。正式数据可采用 maxHp 数值及 `intentSequence: [{"type":"attack","amount":1,"hits":1}]`。模型在回合结束执行当前意图，再推进序列索引并准备下一意图；界面从同一份 intent 读取数字，确保显示与实际伤害一致。当前只实现攻击类意图，其他类型应同步增加规则和图标。

在 `data/battles.json` 的 enemyIds 中引用敌人。E12 使用 mech_boss 与新增机甲战斗图；普通黑帮头目的敌方立绘仍空，避免把对白头像当作战斗图。空战斗图不绘制默认人物或占位卡片，HP、姓名、意图与点击目标区域仍存在。

## 背景与战斗立绘

背景取 Battle.placeId 对应 Place.backgroundAssetId。`cityMapAssetId` 专用于总览地图，不得用于战斗背景。当前主角通过其 Character.battlePortraitAssetId 读取战斗图，对话继续读取 portraitAssetId。敌人使用敌人配置自己的 battlePortraitAssetId。

新增图片复制入 assets 后，在 `assets.json` 注册 ID。战斗 RGB 白底图可设置 whiteKey=true，使用运行时 shader 去白；透明战斗图应设置为 false，避免去掉白色细节。对白立绘当前由 DemoUI.portrait() 无条件应用去白材质，透明对白图不能只靠 false 关闭，还需调整材质应用条件并检查高光。源文件不会被处理或覆盖。

## 回合与动画

临时规则配置了补牌目标三张、结束回合弃置剩余手牌、牌堆空时将弃牌堆洗回。它们只是演示循环的配置决定，文档中的确定数值仍为攻击 1、敌方 HP 3 和敌方攻击 1。

抽牌从牌堆按 0.045 秒间隔并行飞往手牌位置；选牌后 targeting_line.gd 在画布坐标中绘制跟随鼠标的弧线、箭头和目标锁定环。卡牌在 0.16 秒内飞向目标；命中脉冲、伤害飘字和弃牌飞行并行播放，非致命命中立即恢复操作。出牌时立即将该牌从视图手牌字典移除，并关闭其鼠标拦截，避免飞行残影挡住下一次点击。致命命中额外保留 0.24 秒视觉反馈后返回剧情。抽牌和命中时长仍读取 profile.visuals；出牌弃牌尾动画上限为 0.22 秒。所有 Tween 跟随所属场景销毁，不改变模型与存档协议。

进入与退出战斗的花屏由 `shaders/glitch.gdshader` 实现。主场景先锁输入，自下向上覆盖，遮满后替换视图，再淡出。胜利、失败、投降及演练退出共用同一条路径。当前时长为覆盖 0.58 秒、消退 0.32 秒。

## 剧情返回和演练

每场战斗保留 win、lose、surrender 对应的返回节点。模型 outcome 只通知视图结束战斗，视图调用 `Game.battle_exit(result, revision)`；由流程管理器保存结果和历史，再进入正确节点。成功完成战后对白才标记事件完成。开发模拟按钮也使用同一接口。

演练开始时在内存中保存完整冒险状态，用临时独立状态启动战斗；不写入冒险文件。退出或胜负后恢复此前状态，返回菜单。演练不是正式关卡，不授予事件完成标记、信用点或奖励。

## 血量、日期与局外数据

冒险 schemaVersion 2 增加 maxHp、currentHp、currentDay、combat、inventory。初版存档读取时迁移为 HP 100、日期 1，其余原数据保留。存档会校验牌堆实例不重复、敌方生命范围等基本结构。

`healHpPercent` 按最大 HP 计算并封顶。医院和诊所通过 Place.services 调用同一动作。`advanceDay` 仅由明确请求或开发工具调用，日期封顶 7，不自动进入下一周。未给治疗添加费用、限制或耗时。

MetaProfile 使用独立文件，schemaVersion=1，cyberwareState 初始为空。新游戏不清除 MetaProfile。当前义体页面只作内容入口，不修改战斗属性。

当前战斗内临时义体（0.3.23）：角色 `cyberwareIds` 引用 `data/prototype/cyberware.json` 的共用定义，诺伦配置现有六张紫色占位卡，经 `CombatModel.activate_cyberware()` 激活，为下次攻击增加 1 点伤害。0.3.2 改为每张冷却 1 回合（含使用当回合），下个玩家回合恢复紫色并可再次激活；加成仍可叠加；局外页面仍不提供装备。配置随战斗 profile 保存，`usedCyberware` 与 `nextAttackBonus` 随快照恢复。角色列表与兼容规则见[角色义体配置](#角色义体配置)，效果验证见维护文档“战斗临时义体”一节。

## 地图接口

2026-10-11 已修复消费端固定读取 `city_map` 的问题：配置中的 `cityMapAssetId` 现在决定实际显示的底图。字段缺省使用 `city_map`，空值或资源不可用沿用原有地图后备纹理。新增底图时同时注册 `data/assets.json` 的资源、设置 `data/map.json` 的 ID，并重新校准地点锚点。运行 `tests/map_config_tests.tscn` 检查资源替换、缺省／失效后备和原始宽高比。

地图读取 `data/map.json` 的总览插画资源，`cityMapAssetId` 经 [data/assets.json](../data/assets.json) 指向 `assets/map/map.jpg`。底图保持原始比例并统一计算绘制矩形，地点与标记映射到同一矩形。`coordinatesStatus` 当前为 `illustration-calibrated`，[data/places.json](../data/places.json) 的 17 个 `mapAnchor`（0—1 比例坐标）已按本轮插画校准到建筑；`mapDisplay` 的 `offset`／`labelOffset`／`avatarSide` 只用于展示，`hitArea` 是元数据，实际点击命中取自图钉与头像的当前尺寸。更换插画后需要重新校准锚点。

目标与状态查询在 `Game`：`map_target_events()` 返回下一步可推进的主线事件，`map_place_state(id)` 返回地点开放、可用事件、当前、目标与完成状态，两者都通过同一套条件求值过滤事件条件和地点条件。可推进主线按事件 ID 稳定排序，多条主线全部标金色。不要把 `state.targetId`（委托对象）或 `activeEventId`（可能停留在上一次事件）当作地图目的地。

主线 `!` 与可选 `?` 徽章可以同时出现，数量按本类分别统计，为 1 时只显示符号、大于 1 时显示数字。点击地点标记打开浮动详情卡，命中范围是标记本身而不是整幅插画建筑；卡片内任务类型文案为“主线任务”／“可选事件”，底部按钮为“进入地点 →”，按钮再次调用统一的 `start_event()`、`visit()` 或 `heal_at()` 校验。地图治疗不修改 `currentPlaceId`，视图重建后通过 `pending_selection_id` 恢复所选详情。纹理经 `ResourceLoader` 读取已导入资源，符号按 alpha 主体在运行时像素副本上裁切、降到 128 像素并生成 mipmaps，原素材不修改；外框状态由 `scripts/map/frame_state.gdshader` 染亮边。正式复杂的不规则轮廓可在此基础上扩展多边形热点。

悬停预览与详情卡的文字由 `MidnightMapCard` 自己的 `_label` 创建，只复用 `DemoUI` 的字体与主题；节点加入场景树后再设定受限 `size` 并开启 `clip_text`。文字测量与显示统一使用 Font 的 `BREAK_MANDATORY|BREAK_WORD_BOUND|BREAK_ADAPTIVE`，所有 CardLabel 设 `line_spacing=0`；Font 默认断行 flags 与 `Label.WORD_SMART` 不一致，再加上默认行距，会让 48 像素两行文字只露出一行。预览不使用单行 ellipsis，改动文案或字号后重新检查文字边界。

## 牌堆浏览

`pile_view.gd` 是战斗内的模态大界面，使用 ScrollContainer + 五列 GridContainer，复用 CombatCard 的 read_only 预览模式（1.2 倍卡面、不触发选牌、不阻挡滚轮）。网格从内容区域最左侧开始排列，不足一行也不居中。重复实例逐张展示；Esc、右键与返回按钮关闭。浏览时拦截战斗鼠标与快捷键，关闭后恢复原战斗。

展示顺序只对 contents 的副本排序：排序值取可选整数 sortOrder，未填写则取 card_catalog 中的位置；同优先级按卡牌 ID、同卡按稳定实例 UID 排列。不会写回实际 draw_pile / discard_pile，也不会泄露临时洗牌结果。

`tests/pile_visual.tscn` 覆盖空牌堆、真实弃牌、30 张临时容量样本、重复卡、默认／显式排序、滚轮穿过卡面、末行完整可见、输入隔离和关闭。容量样本只在测试内存中生成，不加入正式牌组或存档。

手牌使用 BUTTON_PRESS，在鼠标按下时立即选中并更新指向线。battle.gd 记录本次按住的卡牌 UID；左键松开时重新检测有效目标并只结算一次。空白处松开保留点选模式；取消、出牌与回合忙碌会清理按住状态。只读牌堆卡不启用此输入模式。`tests/drag_visual.tscn` 验证按下起线、拖动松开出牌、取消、重复释放和原点选方式。
