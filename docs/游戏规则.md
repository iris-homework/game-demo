# 午夜委托·第一周 游戏规则

本文面向第一次接触《午夜委托》Demo 的读者，说明当前版本实际能玩到的玩法、目标、地图与事件、选择条件、战斗、治疗与日期，以及奖励、存档、演练和义体的现状。如果你只想看页面之间怎么跳转，请阅读 [游戏流程与路由](游戏流程与路由.md)。

**核对信息**：核对日期 **2026-10-07（Asia/Shanghai）**；基线版本 **0.2.4-r1**（以 [project.godot](../project.godot) 为准），地图页面于同日接入。本文通过 [scripts/game.gd](../scripts/game.gd)、[scripts/combat/combat_model.gd](../scripts/combat/combat_model.gd)、[scripts/map.gd](../scripts/map.gd) 及相关视图与 [data](../data) 下的 JSON 做**文档静态核对**，不重跑剧情与战斗的完整游玩。地图的画面与真实指针输入验收见[地图界面验收清单](地图界面验收清单.md)：本轮已执行 `36-capture-final`（5 checks）与 `37/38/39` 三尺寸输入（各 111 checks，0 failures）。历史处理约定见 [维护文档](维护文档.md) 与 [修改记录](修改记录.md)，功能接入见 [开发接入说明](开发接入说明.md)。

## 实现状态说明

本文用三种标签区分内容，避免把占位或概念当成已完成功能：

- **【已实现】**：当前代码与配置中已有对应实现；本轮未重新做运行验证。
- **【临时原型】**：为了验证流程而临时接的规则或数值，不是正式定稿，正式内容会替换它。
- **【设计未实现】**：只有字段、按钮、空目录、概念稿或 Word 文本，运行时不会产生对应效果。

对话、事件、地图与战斗的界面都属于原型展示层；正式卡面、正式敌人数值、费用体系、第二与第三周内容尚未实现或定稿。用户已删除工程同级的原始资料目录；工程内保留的方案与概念稿**不是已实现功能的证明**。

## 玩法循环

当前是第一周的原型流程：单主角诺伦在城市里接下委托，通过城市总览地图选择地点和事件，用对白与选择推进剧情，在部分事件中进行临时卡牌战斗，最后走到事件结算。【已实现】

一次完整的循环如下：

1. 从主菜单选择"开始新的委托"或"继续旅程"。
2. 新游戏直接进入 **E01"午夜酒馆"** 的对白，在酒馆里接下委托并选择追踪目标（理查德或卢米娜）。已有进度时，菜单会先要求确认覆盖；新冒险不清空局外义体档案。
3. 进入**城市地图**。地图上可以查看地区详情，也可以直接开始当地事件，或先“进入地点”。
4. 事件由对白节点与选择推进；其中一部分事件包含一场战斗，另一部分没有战斗。
5. 战斗结束（自然胜利、自然失败或主动投降）后，按该战斗的 `returnNodeByResult` 回到对应剧情节点。
6. 事件走到 **`finish` 节点**时才真正结算：事件被记为完成，并进入事件结算页。
7. 在结算页确认奖励后回到城市地图。完成 E12 的 `finish` 会标记第一周完成。

移动、对白推进、出牌、结束回合和治疗都**不会**自动推进日期；第二、第三周目前没有内容。

## 目标与阵营

### 目标

界面上的目标文字由 [game.gd](../scripts/game.gd) 的 `objective()` 决定。【已实现】

- 当 `flags.week1Complete` 为真时显示"第一周已完成 · 可继续探索支线"。
- 否则取当前可开始事件中的第一个**主线事件**（`optional` 为假），显示"事件标题 / 地点名"。
- 若没有可开始的主线事件，显示"探索城市，寻找新的线索"。

推进主线的关键在于：在 E01 选定追踪目标，取得后巷线索与港口线索，在港口完成对应阵营入口，再完成本阵营的发电厂任务，最后在 E12 结束第一周。

### 阵营

阵营字段为 `state.faction`，只接受 `company`（公司）、`resistance`（革命军）或空字符串。【已实现】

- 完成 **E05A**（理查德线）会把阵营设为 `company`。
- 完成 **E05B**（卢米娜线）会把阵营设为 `resistance`。
- 阵营决定后续可进入的地点与可开始的事件：公司线开放沃斯大楼并解锁 E09，革命军线开放革命军营地并解锁 E10。
- E12 的解锁条件为"完成 E09 **或** E10"，因此两条阵营线都能走到第一周结局。

### 委托目标

委托目标字段为 `state.targetId`，只接受 `richard`、`lumina` 或空字符串。E01 的选择会写入该字段，之后的 E05A / E05B 分别要求 `richard` / `lumina`，对白中的 `{目标姓名}` 会替换成对应人物名（理查德 / 卢米娜）。若目标名缺失或出现未知变量，运行时会报配置错误。【已实现】

## 地图、地点与事件

### 城市地图页面

地图页面读取 [data/map.json](../data/map.json) 的 `cityMapAssetId`（经 [assets.json](../data/assets.json) 的 `city_map` 指向 `assets/map/map.jpg`）。底图按原始比例铺排，16 个地点以图钉尖端锚定到对应建筑。【已实现】

- `coordinatesStatus` 为 `illustration-calibrated`，即 16 个 `mapAnchor`（0—1 比例坐标）已按本轮底图逐个校准。`mapDisplay` 的 `offset`／`labelOffset`／`avatarSide` 只影响展示，`hitArea` 仅作元数据，实际点击命中取自图钉与头像的当前尺寸。
- 地图符号从 `assets/icons/map/` 的 17 份素材中复用 16 份，对应 16 个运行时地点；义体教会的 `church.png` 不接入运行时，只作为插画地标参考，没有对应的游戏地点或事件。革命军营地在运行时的地点名仍是“革命军营地”。
- 标记高度为逻辑 48 像素。当前位置显示青色标记与圆形诺伦头像；下一步可推进的主线目标显示金色图钉。两者落在同一地点时同时出现。
- 事件徽章：主线与可选分别显示 `!`／`?` 两枚角标，可以同时出现；数量按本类分别统计，不是两类合计。数量为 1 时只显示符号，大于 1 时在符号后显示数字。另有锁与勾区分尚未解锁和已完成、暂无新事件的地点。
- 选中地点显示浅色外圈，不改变原有状态颜色。悬停约 0.2 秒出现只读简介与任务信息；点击固定单卡，已有固定卡时悬停其他地点只高亮，不替换固定卡。
- 详情面板列出该地点的描述与可开始事件，任务类型文案为“主线任务”与“可选事件”，点击事件按钮调用 `start_event()`；已解锁且含服务时显示“治疗 · 回复 30% 最大 HP”，底部提供“进入地点 →”。空白处或 Esc 关闭详情，周次弹窗存在时 Esc 先关闭弹窗；详情靠近窗口边缘会自动翻转或平移，不移动底图。长标题与多事件可垂直滚动，底部按钮保持可用。
- 地图上的“周次档案”弹窗显示第一周进度与第几天，并注明第二、第三周内容待设计。

目标由 `Game.map_target_events()` 推导：按事件 ID 稳定排序，多条可推进主线全部标金色，不任意选择其中一条。`state.targetId` 是委托对象字段（理查德／卢米娜），`activeEventId` 可能停留在上一次事件，二者都不作为地图目的地。

地图直接治疗调用同一个 `heal_at()`，不改变 `state.currentPlaceId`；治疗引起的视图重建会在原地恢复所选详情。从地点返回地图时从干净总览开始。地图采用总览插画加点击标记的交互方向，不制作小人跑图、行走动画、寻路或碰撞。美术方向见 [美术方向](美术方向.md)，实际结果与证据见 [修改记录](修改记录.md) 与 [地图界面验收清单](地图界面验收清单.md)。

### 事件可用性

正常地图或地点流程中，要开始一个事件，必须同时满足【已实现】：

1. 未出现在 `completedEventIds` 中；
2. 满足事件自身的 `unlockCondition`；
3. 其所在地点已解锁（`place.unlockCondition`）。

`available_events()` 本身只过滤完成状态与事件条件；地图展示时检查地点是否开放，`start_event()` 再校验地点条件。不要把事件列表函数单独当作完整的进入权限判断。

所有第一周事件的 `repeatPolicy` 都是 `once`，当前通过完成列表阻止事件重复触发。事件列表排序把主线事件排在可选事件之前。

## 选择、条件与信用点

### 条件

对白节点和事件可用性都用同一套 `meets()` 条件求值，支持的键为：【已实现】

| 条件键 | 含义 |
| --- | --- |
| `all` | 列表内全部条件成立 |
| `any` | 列表内至少一个条件成立 |
| `completed` | 指定事件 ID 已完成 |
| `flag` | 指定旗标为真 |
| `faction` | 当前阵营等于指定值 |
| `target` | 当前委托目标等于指定值 |
| `creditsAtLeast` | 信用点不少于指定值 |

出现未知条件键时，`meets()` 会输出错误并返回假，不把未知条件当作成立。

### 选项

对白选项在对话节点里以 `choices` 数组定义，每个选项包含 `id`、`label`、`next`，可选 `condition` 与 `effects`。【已实现】

- 不满足 `condition` 的选项按钮会被禁用；若缺的是信用点，按钮文字会追加"（还差 N CR）"。
- 选择后先校验目标节点和效果，再整批提交 `effects`，最后进入 `next` 节点。
- 若 `next` 是 `@map`，表示返回城市地图。
- 已做过的选择会记录在 `choiceHistory` 中，键为"事件 ID : 节点 ID"。
- 选项效果实行**全有或全无**：任一条效果校验失败，整个选择都不提交。

### 效果

事件选项与 `finish` 节点都能使用效果动作，当前支持：【已实现】

| 动作 `op` | 作用与限制 |
| --- | --- |
| `setFlag` | 写入一个旗标；键不能为空 |
| `spendCredits` | 扣信用点；额度不足则失败 |
| `addCredits` | 增加信用点；负数失败 |
| `setTarget` | 设置委托目标；只接受理查德 / 卢米娜 |
| `setFaction` | 设置阵营；只接受公司 / 革命军 / 空 |
| `completeEvent` | 把指定事件记入已完成列表 |
| `healHpPercent` | 按最大 HP 比例回复，封顶最大值；比例须在 0—1 |
| `advanceDay` | 推进天数；日期封顶第 7 天 |
| `finishWeek` | 设置 `week1Complete` 旗标 |
| `grantReward` | 按奖励 ID 发放信用点奖励；同一"事件:奖励"只发一次 |

### 信用点

信用点是当前实现的支付货币，初始数量与支付分支用于原型验证。【临时原型】

- 新游戏初始信用点为 **0**（见 [config.json](../data/config.json) 的 `initialCredits`，注释说明为演示值）。
- 目前**唯一**需要支付的选项是 E03 支付艾克 **300 信用点**买情报（条件 `creditsAtLeast: 300`）。初始为 0，所以正常开局无法直接支付，需要 F1 开发面板测试支付分支，或拒绝支付改用战斗路线。
- 奖励目录 [rewards.json](../data/rewards.json) 当前为空对象，`grantReward` 只支持 `type` 为 `credits` 的奖励。

## 战斗

### 临时规则

战斗规则的数值来自 [data/prototype/combat.json](../data/prototype/combat.json)，是**临时原型**，不是正式定稿：

- 牌组为三张"临时攻击"，每张造成 **1 点伤害**；`cost` 为 `null`，**不计算费用**。
- 手牌补牌目标 `handSize` 为 **3**。
- 敌人默认最大生命 **3**，默认意图为**攻击 1**。
- 回合结束时**弃置剩余手牌**（`discardHandAtTurnEnd`）。
- 抽牌堆空时**回收弃牌堆并洗牌**（`recycleDiscardWhenEmpty`）。

`handSize` 是 `draw_cards()` 的补牌目标，不是所有效果通用的手牌硬上限。首次牌组按配置正序放入抽牌堆，再从末尾抽取，因此首次实际抽取顺序与配置顺序相反；只有在回收弃牌堆时才会洗牌。

### 出牌与手牌

【已实现】

- 按下手牌即选中并显示指向线；按住拖到有效敌人松开出牌，也可以先点选再点击敌人出牌。
- 指向有效敌人时箭头变洋红并显示锁定环；再次点同一张牌、右键或 Esc 取消，取消后松开不会出牌。
- 出牌顺序为：按下选牌 → 目标确认 → 模型校验并结算 → 保存快照 → 播放命中与弃牌表现。
- 一次出牌先校验目标存活、牌仍在手、效果受支持，再统一改 HP、移入弃牌堆并判断结局；重复点击或重复释放不会二次消费同一张牌。
- 每张卡结算后飞入弃牌堆；命中飘字与弃牌动画不阻塞下一次选牌。

点击抽牌堆或弃牌堆会打开只读的大尺寸浏览界面：每行最多五张完整卡面、重复卡逐张保留、可垂直滚动、按卡牌配置默认顺序排列。浏览界面只对副本排序，不会改变实际抽牌或弃牌顺序，也不允许出牌。

### 回合

【已实现】

1. 回合开始（首次为战斗起点）按补牌目标抽到三张手牌。
2. 玩家可以依次出牌，也可以直接点击"结束回合"。
3. 结束回合时，剩余手牌被弃置，敌人依次执行当前意图（当前只有攻击类）。
4. 若玩家生命降到 0，战斗判负；否则回合数 +1，敌人意图索引前进并准备下一次意图。
5. 补牌到三张后进入下一回合。

### 胜负与投降

【已实现】

- **胜利**：所有敌人生命降到 0 即 `win`。原型为单敌 3 HP，三张攻击卡即可自然获胜。
- **失败**：玩家生命降到 0 即 `lose`。
- **投降**：战斗界面单独提供"投降"按钮，产生 `surrender`；它不是模型判定，而是玩家主动请求。
- 开发模式下还有"调试结果"弹窗，可模拟胜利或失败，仅用于验证剧情返回。

只要玩家 HP 在进入战斗时已经为 0，战斗初始化就会直接判定为 `lose` 并进入失败流程。因此开放治疗地点并先恢复生命是必要的。

三种结果都通过 `battle_exit(result, revision)` 处理：校验当前确实在战斗中、请求未过期、该战斗的 `returnNodeByResult` 含该结果，然后跳转到对应节点，并记录 `battleHistory`。具体返回节点见 [游戏流程与路由](游戏流程与路由.md) 的战斗返回表。

### 当前战斗边界

【设计未实现】或已知限制：

- 模型支持 `enemies` 数组，但界面与验收以**单敌、三张手牌**为准；多敌布局与大量手牌未完整验收。
- 敌人当前只执行 `attack` 意图，HUD 也固定显示攻击；其他意图只填 JSON 不会生效。
- 能量、格挡、状态、升级、消耗、稀有度与正式牌组构筑均未实现。正式卡牌目录 [cards.json](../data/cards/cards.json) 为空。
- [cards/schema.json](../data/cards/schema.json) 只是预留结构说明，运行时**不加载**它做校验，而且它只要求 `id`，弱于代码实际需要的字段。
- 道具接口 `use_item()` 当前**一律拒绝**：正式道具目录 [items.json](../data/items/items.json) 为空，底部道具栏三个槽位禁用并提示"道具待配置"。
- 敌方战斗立绘缺失时保持透明空位，但姓名、HP、意图和点击区域仍然存在；只有诺伦与复仇机甲接入了战斗立绘。
- 已开始的战斗快照包含当时的规则与卡目录，之后修改 JSON 不会更新进行中的旧战斗。

## 治疗与日期

### 治疗

【临时原型】医院与地下诊所通过地点服务 `healHpPercent` 治疗：

- 每次恢复**最大 HP 的 30%**，封顶到最大值。
- 原型阶段**免费**、**不耗时**，没有其他次数或费用限制。

服务由 `heal_at(place_id)` 统一处理，要求当前在地图或地点页；治疗成功后写入检查点并弹出提示。

### 日期

【已实现】

- 新游戏为**第 1 天**，日期范围 1—7。
- 移动、对白、出牌、结束回合和治疗都不会自动推进日期。
- 只有明确请求或开发工具才会调用 `advanceDay`，且日期封顶第 7 天，不会自动进入下一周。
- 完成 E12 的 `finish` 会设置 `week1Complete`，但**不会**改变日期。
- 第二、第三周在 [week2](../data/weeks/week2/week.json)、[week3](../data/weeks/week3/week.json) 中只有 `status: pending` 的占位，没有事件。

### 开发面板

F1 在开发模式下打开面板，可把信用点设为 0 或 300、日期 +1，以及把 HP 设为 50 / 90 / 1 / 100。它只修改当前检查点，用于测试支付与受伤分支。【临时原型】

## 奖励、存档、演练与义体

### 奖励领取

【已实现】事件结算页读取事件的 `rewardIds`：

- 若事件没有奖励，按钮显示"返回城市地图 →"。
- 若有奖励，按钮显示"领取并返回城市地图 →"，列出"可领取 / 已领取"状态。
- 两个按钮都走 `claim_rewards()`：按奖励 ID 逐个发放，然后返回城市地图。
- 发放以"事件 ID : 奖励 ID"为键记录在 `claimedRewardIds` 中，同一奖励不重复发放。

当前所有第一周事件的 `rewardIds` 都为空，奖励目录也为空，因此实际画面统一显示"本次无奖励"与"返回城市地图 →"。【设计未实现正式奖励池】

### 存档

【已实现】

- 冒险检查点为 `user://checkpoint.json`，备份为 `checkpoint.json.bak`，写入中间文件为 `.tmp`。
- 冒险存档 `schemaVersion` 为 2，包含 HP、最大 HP、天数、战斗快照、物品栏、剧情状态等；自动读取版本 1 存档并迁移为 HP 100、日期 1。
- 保存时先写 `.tmp`，把旧主文件复制为 `.bak`，再替换主文件；加载依次尝试主文件与备份，再迁移与校验。`.bak` 是上一次主文件的副本，**不保证一定有效**。
- `checkpoint()` 与 `commit_combat()` 不检查保存函数返回值：写盘失败会提示，但内存状态已经提交，不会自动回滚。
- 因此逻辑结算成功不代表一定可靠落盘；遇到保存错误应先排查权限与磁盘。

备份轮换、迁移范围与恢复步骤的完整说明见 [维护文档](维护文档.md) 的存档章节。请勿用测试存档覆盖正式玩家进度。

### 战斗演练

【临时原型】主菜单提供两个演练入口，用于查看战斗而不影响冒险：

- "战斗演练"从后巷事件进入战斗，
- "机甲演练"从蜂巢城寨事件进入复仇机甲战斗。

演练的隔离规则【已实现】：

- 开始前把当前冒险状态备份到内存，然后用全新临时状态进入战斗；期间**不写入冒险存档**。
- 退出或分出胜负后恢复之前的冒险状态，返回**主菜单**，并提示"冒险进度和血量未改变"。
- 演练**不授予**事件完成标记、信用点或奖励，也不是正式关卡。
- 演练从事件中名为 `battle` 的节点进入；新增演练入口时该节点必须存在并指向正确战斗。

### 义体档案

【已实现】主菜单有"义体档案"入口，读取独立的局外资料 `meta_profile.json`（`schemaVersion` 为 1，初始 `cyberwareState` 为空）。该文件不随新冒险重置。

【设计未实现】当前没有可选义体和装备效果，页面**不发放物品，也不改变冒险或战斗属性**。义体目录 [cyberware.json](../data/cyberware/cyberware.json) 为空。
