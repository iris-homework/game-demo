# 午夜委托项目维护文档

本文面向继续开发本项目的人或 AI 助手，说明改动位置、需要保持的行为、测试方法和故障排查顺序。维护目标是减少功能回退、重复结算、存档丢失和界面误操作；测试覆盖的是当前原型，扩展规则时仍需补充对应检查。

核对日期：**2026-10-03，Asia/Shanghai**。当前基线：**0.2.3-r1**，Godot **4.7.2 standard / Compatibility**，逻辑画布 **1440×900**，默认窗口 **1280×800**，缩放模式为 `canvas_items`。其他 Godot 4.x 版本尚不能视为已验证。

历史变化见 [修改记录](修改记录.md)，功能接入参考 [开发接入说明](开发接入说明.md)，历史原始输出见 [验收记录](验收记录.txt)。本文描述当前代码；文中标明“扩展前需要处理”的内容尚未实现。

## 开始修改前

1. 先确认需求涉及哪一层，并查看下表和相关函数。保持用户最近确认的行为，尤其是按下立即瞄准、牌堆左对齐及默认排序。
2. 留下可恢复的工程副本或版本提交。当前交付包使用固定文件名，反复覆盖它不能替代版本历史；备份时使用版本号和日期区分。
3. 涉及存档、数据 ID 或战斗规则时，先备份用户存档，并阅读本文存档章节。
4. 为改动选定验收场景。逻辑缺陷补有意义的回归测试；小型文案、配色或对齐调整通常做实际画面检查即可。
5. 完成后更新修改记录、必要的维护说明和工程包。未运行的检查明确写“未运行”，不沿用旧通过结果。

原始 Word 文档和 `卡牌游戏美术资源` 目录在工程之外，作为设计与素材来源保留。修改工程内代码或素材副本，不用临时测试数据覆盖原始内容。

## 当前规则与尚未实现的内容

当前临时牌组在 [data/prototype/combat.json](../data/prototype/combat.json)：三张攻击卡、单次伤害 1、敌人默认 3 HP、意图攻击 1。新冒险默认 100 HP、第 1 天；日期不会因出牌或移动自动推进，最多到第 7 天。

正式卡牌、道具和义体目录仍为空，正式奖励池也未填充。能量、格挡、状态、升级、消耗牌、多敌界面完整布局、后续周次和正式城市总览插画没有完成。预留字段或按钮不代表规则已经支持。

当前 `handSize` 是 `draw_cards()` 的补牌目标，不是所有效果通用的手牌硬上限。首次牌组由 `profile.deck` 正序放入抽牌堆，再从末尾 `pop_back()` 抽取，因此首次实际抽取为配置倒序；只有弃牌回收时会洗牌。牌堆浏览界面的排列与这些抽取规则无关。

## 出牌流程必须保持的约定

一次出牌的顺序为：**按下选牌 → 目标确认 → 模型校验并结算 → 保存快照 → 播放命中与弃牌效果**。

### 按下与释放

- 手牌的 `card_button.action_mode` 使用 `BUTTON_PRESS`，按下即触发 `begin_card_aim()`；不要改回释放后选中。
- `selected_uid` 表示选中的实例，`held_card_uid` 只表示这一次鼠标按住的实例。卡牌定义 ID 不能代替实例 UID，否则同名卡容易被一起移除或重复使用。
- 左键释放时先清空按住状态，再重新检测目标。不能只使用上一帧的 `hovered_target`，也不能在两个信号回调里各提交一次伤害。
- 空白处松开保留点选模式；再次点选同一张牌、右键或 Esc 取消。取消后再松开左键不能出牌。
- 目标检测、箭头终点和卡面起点使用同一画布坐标体系。保持 `get_global_mouse_position()` 与卡牌 `get_global_transform()` 的转换，不混入桌面屏幕坐标。

### 模型提交与动画

`CombatModel.play_card()` 先验证目标、牌是否仍在手中及效果，再改 HP、移入弃牌堆并判断结局。视图随后调用 `Game.commit_combat()` 保存快照。重复点击和重复释放不得再次消费同一 UID。

当前非致命起手约 0.16 秒，命中后恢复操作；弃牌尾动画和飘字可继续播放。飞行卡牌必须立即移出视图的 `cards` 字典，并将本体和按钮的 `mouse_filter` 改为忽略。否则残影会挡住下一次点击，或回合回收时出现重复卡面。

`set_busy(true)` 会清理按住状态并禁用手牌。新入口应检查转场锁 `transition_locked`、战斗忙碌 `battle_busy` 和牌堆弹层是否存在。致命命中、回合切换及转场期间继续锁定输入。Tween 随所属场景销毁；尾动画不应再修改战斗模型。

**战斗提交使用 `commit_combat()`，不能用 `checkpoint()` 替代。** 前者更新快照并发送 `status_changed` 更新 HUD；后者发送 `changed`，会触发视图重建。动画中误用后者可能销毁正在使用的卡牌节点。

`revision` 用于对白、选项和战斗退出的过期请求检查；`commit_combat()` 本身没有调用者 revision 校验。新增异步规则或多个提交来源时，需要另行处理过期状态，不能假定已有检查覆盖所有写入。

## 牌堆和按钮维护

牌堆浏览使用 `contents.duplicate()` 建立展示数组。默认排序键为：定义中的 `sortOrder`，未填写则使用卡目录位置；再按卡牌 ID、实例 UID 排列。`sortOrder` 是直接参与排序的数值，不是“所有设置了此字段的牌都排在前面”。

保留以下表现与输入约定：

- `GridContainer.columns = 5`，水平布局使用 `SIZE_SHRINK_BEGIN`。一张或两张牌也从最左边开始，不居中；重复卡逐张展示。
- 只读卡使用 `setup(..., true)`。它们可以显示卡面和悬停反馈，但不连接战斗出牌、不执行抬升位移，不截断滚轮传递。
- `ScrollContainer` 负责垂直滚动；调整卡面缩放时同步调整格子大小、间距和可视高度，检查最右列及最后一行完整可见。
- 弹层拦截底层按钮和快捷键；Esc、右键或返回按钮关闭弹层，不能直接退出战斗。关闭回调可能立即移除节点，标记输入已处理应发生在移除之前。
- 通用按钮通过 `DemoUI.button()` 创建，保留居中文字与对称内边距。无文字的敌方点击区域单独处理，避免把按钮角标画在立绘上。

## 增加卡牌和敌人的步骤

1. 在正式目录中定义唯一、稳定的 ID，检查 `battles.json`、`characters.json`、`assets.json` 等引用。正式卡与临时卡不要使用相同 ID；当前合并规则会保留正式目录中的同名定义。
2. 卡牌准备名称、说明、资源引用、费用字段和效果。当前执行器仅支持非负 `damage`，数值转成整数；维护时使用明确整数。空效果数组目前可以被打出并弃置，但不会造成伤害，不是完整的合法性校验。
3. 新效果须先实现模型的验证、执行和快照语义，再接入卡面说明、目标选择及动画，补充成功、非法目标、重复提交与读档测试。
4. 敌人目前只执行 `attack` 意图，HUD 也固定显示攻击。其他意图只填 JSON 会出现规则不执行或显示不符，需同时实现模型与展示。
5. 创建战斗时先 `CombatModel.new()` 再 `initialize()`。当前 `initialize()` 不清空旧模型，不支持安全地在同一对象上反复初始化。
6. 改卡牌或敌人数值后用新战斗验收。已有战斗快照包含 `profile`、`cardCatalog` 和敌人数据，修改 JSON 不会自动更新进行中的旧战斗；需要保留旧规则或显式迁移。
7. 新增演练入口时检查其事件确有名为 `battle` 的节点，并引用对应战斗。当前 `start_training()` 固定从这个节点进入。

`data/cards/schema.json` 是预留结构说明，当前运行时没有加载它进行验证，而且它只要求 ID，弱于代码实际需要的字段。JSON 能解析或存档通过基础校验，不代表所有内容引用及效果正确。新增正式内容后，还要同步调整测试中“正式目录为空”等原型专用断言，保留有效的业务检查。

## 立绘与界面资源

- 对白读取 `portraitAssetId`，战斗读取 `battlePortraitAssetId`；缺失战斗图保持空位，不自动换成对白图。敌方 HP、意图及目标区域仍要存在。
- 背景取当前战斗地点的背景资源；城市总览使用独立 `cityMapAssetId`。港口背景不替代城市地图。
- 白底图在运行时通过 `white_key.gdshader` 去白。战斗图受 `assets.json` 的 `whiteKey` 控制，透明战斗 PNG 应关闭它。
- **对白立绘当前无条件挂去白材质。** 更换为透明对白 PNG 时，仅设置 `whiteKey=false` 不生效；需要同时调整 `DemoUI.portrait()` 的材质应用条件，并确认白色衣料与高光未被抠除。这是现有差异，尚未统一开关。
- 检查深色背景下的发丝、披风、机械轮廓及面部高光，并在实际窗口尺寸下查看。不要为去白直接覆盖原始美术。
- 中文字体位于 `assets/fonts`，按钮使用其 FontVariation。更换字体时检查中文缺字、按钮居中、小字号和随附字体许可。

## 存档维护与恢复

默认冒险文件为 `user://checkpoint.json`，备份为 `checkpoint.json.bak`，写入中间文件为 `.tmp`。macOS 当前目录为：

```text
~/Library/Application Support/MidnightCommissionDemo/
```

局外资料使用同目录下的 `meta_profile.json`。冒险 schemaVersion 为 2，Meta 为 1；UI 版本提升不会自动改变这两个格式。

### 必须区分的实际行为

- `checkpoint()` 和 `commit_combat()` 不检查 `save_game()` 的返回值。写盘失败会提示，但内存状态已经提交，不会自动回滚或停止；逻辑结算成功不代表已经可靠落盘。出现保存错误时，先排查权限和磁盘问题并尽量保留当前进程状态，不要假定重启后能恢复刚才进度。
- 冒险保存先写 `.tmp`，再复制旧主文件到 `.bak`，最后替换主文件。**`.bak` 是上一次主文件的副本，不保证一定有效**；当前代码没有校验旧主文件或检查复制结果。
- 加载依次尝试主文件和备份，迁移后再校验。只存在一个文件不代表可以成功继续游戏。
- `migrate_save()` 仅实现冒险版本 1 到 2。新增存档字段或删除既有 ID 时，同步改初始化、迁移、校验及旧档测试，不只修改版本数字。
- `valid_combat()` 检查基础字段、HP 范围、UID 唯一性与三个牌堆的实例守恒，但不完整校验所有效果和意图结构。
- Meta 只有 `.tmp` 替换，没有 `.bak` 恢复；加载失败时保留默认空资料。新游戏不主动清空正常加载的 Meta。
- `save_game()` 和 `save_meta()` 的函数内部没有 `save_enabled` 保护。调用方负责隔离；测试如直接调用保存，必须改为测试专用文件路径。

### 遇到损坏或不兼容存档

1. 退出游戏，先复制整个存档目录到单独的带日期备份。不要先删文件或开始新游戏。
2. 使用备份副本调查，记录游戏版本、Godot 版本、事件节点和错误输出，查看 `load_game()`、迁移及校验失败位置。
3. 程序会尝试 `.bak`。若从备份恢复成功，先保留这份备份的独立副本，再保存新进度；因为下一次保存可能先用损坏的主文件覆盖 `.bak`。
4. 两份文件均无效时，保留它们供修复或迁移。不要用测试存档替代玩家进度。
5. 回退程序前检查旧版本能否读取当前 schema。当前没有版本 2 降回版本 1 的迁移；旧代码与旧存档应配套恢复。

## 已知边界与扩展前检查

| 边界 | 当前证据 | 需要处理的情形 |
| --- | --- | --- |
| 首回合空手恢复可能额外补牌 | `start_hand()` 用“第 1 回合且空手”判断首次发牌；这是代码审查推导，本轮未运行专门复现 | 提高敌人 HP 后，首回合打完牌但未胜利，返回菜单再继续。扩展前增加独立首次发牌状态或等效判断，并补回归测试 |
| 配置缺少完整启动校验 | `read_data()` 直接解析，卡牌 schema 不在运行时验证 | 开始大量配置正式内容前，增加字段和引用校验，或保证导入流程验证 |
| 多敌与大量手牌尚未完整验收 | 模型有 enemies 数组，现有界面与原型以单敌、三张手牌验收 | 扩展敌人数量、手牌规模时检查重叠、目标区域、卡面文字与可达性 |
| 已存战斗保留旧配置 | 快照含规则与卡目录 | 平衡性更新后，需要新战斗验收或明确的存档迁移策略 |
| 备份轮换与对白去白开关存在限制 | 见前两节的实际代码行为 | 不把文件备份或 whiteKey 开关当成对所有数据、所有立绘均通用的保证 |

上述边界未在本次文档整理中修改代码。默认敌人 3 HP 的已验证流程不能代替扩大数值范围后的测试。

### 可执行命令

以下命令在 `MidnightDemo` 目录执行。macOS 使用现有安装路径；其他安装位置替换 `GODOT_BIN`。也可在 Godot 中打开指定测试场景后按 F6，图形测试需要真实窗口。

```sh
GODOT_BIN="/Applications/Godot.app/Contents/MacOS/Godot"
"$GODOT_BIN" --headless --path . --editor --import --quit
"$GODOT_BIN" --headless --path . res://tests/run.tscn
"$GODOT_BIN" --headless --path . res://tests/combat_tests.tscn
```

按需逐个运行下面的图形检查，不要并行。交互测试会移动系统鼠标并注入点击，执行时不要手动操作测试窗口；发生失败时先保留错误与复现条件，不能把所有失败直接归为鼠标干扰。

```sh
"$GODOT_BIN" --path . res://tests/r1_visual.tscn
"$GODOT_BIN" --path . res://tests/interaction_visual.tscn
"$GODOT_BIN" --path . res://tests/pile_visual.tscn
"$GODOT_BIN" --path . res://tests/drag_visual.tscn
```

需要检查另一窗口尺寸时，在相应命令中加入 `--resolution 1600x1000`。图形场景不能用 `--headless` 代替。`tests/visual.tscn` 是早期截图脚本，当前优先使用上面的专门测试。

检查退出码之外，还要检查输出是否含 `SCRIPT ERROR`、`Parse Error`、`ERROR`、失败断言或等待超时。编辑器导入进程正常退出不能单独证明脚本无错误；缺少最终测试汇总也不能算通过。

## 常见问题排查

| 现象 | 首先检查 |
| --- | --- |
| 必须松开鼠标才出线 | `card_view.gd` 是否仍为 `BUTTON_PRESS`，`chosen` 是否接到 `begin_card_aim()` |
| 取消后松开仍出牌或扣两次血 | `held_card_uid` 清理、释放回调是否重复、模型 UID 是否已移出手牌 |
| 线跟鼠标有偏移 | 全局画布坐标转换与 `canvas_items`，是否误用桌面坐标 |
| 连续出牌发卡或点击被吞 | 飞行卡是否仍接收鼠标、是否等尾动画才解锁、hover Tween 是否与重新排手牌冲突 |
| 打开牌堆改变了下次抽牌 | 是否直接 `sort()` 了模型牌堆，而非 `duplicate()` 后排序 |
| 少量牌又出现在中间 | `pile_view.gd` 的 `SIZE_SHRINK_BEGIN` 是否被改回居中 |
| 滚轮放在卡牌上不滚动 | 只读按钮的鼠标传递、滚轮透传、外层滚动容器与格子尺寸 |
| 弹层打开时还能结束回合或退出战斗 | 模态层级、鼠标遮挡、键盘事件是否在移除弹层前标记已处理 |
| 改 JSON 后旧战斗没变化 | 快照是否保留旧 `profile` 和 `cardCatalog`；先新开一场战斗验证 |
| 立绘白边或白色细节消失 | 共用 shader、素材是否透明、对白与战斗去白条件差异 |
| 继续游戏失败或重新补牌 | 保存版本与 ID 校验、主档／备份，再检查首回合空手恢复边界 |
| 画面更新时卡牌节点消失 | 是否误用 `checkpoint()` 引发整页重建，或旧异步回调访问已移除视图 |
